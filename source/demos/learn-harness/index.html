01

Mental Model

定位与心智模型：一切皆插件

DeepSeek Harness（命令名 dsh）是一个 agent harness：把模型、工具、会话记录、执行环境和界面组合成可运行的智能体产品。它最反直觉的地方不是功能，而是装配方式。

1.1它到底负责什么

把一次智能体运行拆成四层，dsh 负责把它们接起来，而不是替你把每一层写死：

01 · MODEL

模型

流式请求、重试、token 计量、推理强度；适配器可换（DeepSeek、pi-ai、回放）。

02 · ACTION

工具与执行

工具注册、准入、审批、沙箱、文件系统、子进程、终端、LSP、子代理。

03 · MEMORY

会话

append-only 事件日志、surface 投影、压缩、持久化、检索与分叉。

04 · SURFACE

界面与协议

Web / Desktop / Headless / SDK / ACP，共享同一套 Host 服务与 Remote 传输。

1.2“没有特权内核”是什么意思

很多 agent 框架有一个中心循环，插件只能挂 hook。dsh 的选择相反：模型适配器、工具注册表、会话日志、甚至 agent loop 本身都是插件，都由配置装配，都可以被替换。

Key idea

扩展 dsh 的方式不是“改内核”，而是在旁边挂一个插件；所有注册都是可回滚的 effect，插件卸载时自动解开。这个设计让 HMR、按 profile 组合、以及同一份代码跑在 Web/Desktop/SDK 里成为可能。

代价也很真实：你需要理解装配顺序、服务依赖与事件语义，否则会“注册了但没生效”。这正是后面第 02 节和第 08 节要解决的问题。

1.3Cordis 的五个概念

dsh 构建在 vendored 的 Cordis 之上。只需要先掌握五件事：

CONCEPT 01

插件是一个对象

函数插件导出 name / inject / Config / apply(ctx)；或者是一个 Service 子类。服务包默认导出服务类，函数插件禁止再默认导出。

CONCEPT 02

上下文是服务仓库

服务用稳定的 ctx.<key> 注册，例如 ctx.sessions、ctx.tools、ctx.llm。其他插件按键查找，而不是 import 具体实现。

CONCEPT 03

依赖即加载顺序

inject 声明需要的服务。Cordis 等到服务可用才激活插件，所以启动顺序由依赖表达，不靠手写 boot 序列。

CONCEPT 04

事件是扩展点

事件名通过 TypeScript 声明合并声明，按 emit / waterfall / parallel / serial / bail 派发。interception 优先用事件。

CONCEPT 05

注册即 effect

提示词段、工具 schema、适配器、提供者、监听器都通过 ctx.effect() / ctx.on() 安装，返回 disposer。卸载、热重载、测试清理都沿同一条路回滚。仓库规则：注册必须证明可释放。

五种派发模式，先记这张表

模式是否等待顺序有返回值典型用途
emit否注册顺序观察无通知、遥测、UI 增量
waterfall否包裹式，next() 委托有拦截与改写请求、工具策略、pre-step
parallel是并行无扇出清理、并发通知
serial是注册顺序有顺序决策、turn-stopping 检查点
bail否直到有人返回非空值有“第一个有意见的人说了算”
高频错误

waterfall 监听器如果只观察、却不调用 next()，就会短路整条链。反过来，想独占决策的监听器必须明确不调用 next()。包装时还要保留下游的 startsRequestSeries 等字段。

1.4三条不变量

如果只记三句话，记这三句。后面每个机制都是它们的推论：

  1. Model-visible ⟺ logged. 任何进入模型请求的内容，都必须能从会话日志重建；新的模型可见输入必须新增会话事件。
  2. 注册即 effect. 贡献走 ctx.effect() / ctx.on()；注册函数返回 disposer，卸载可预期地回卷。
  3. 依赖接口，不依赖实现。 扩展插件依赖 Service Definition（例如 dsh-agent、dsh-llm），而不是具体提供者（例如 agent-loop、llm-deepseek）。

1.5几个常见误解

“换 loop = 换框架”

不是。loop 只是 AgentFactory 的一个实现；UI、工具、持久化只认 ctx.agents 的契约。

“会话就是聊天记录”

不是。会话是事件日志，聊天记录是它的一个投影；另一个投影是模型历史，二者在压缩时故意不同。

“工具调用就是函数调用”

不是。每次调用都要经过准入、守卫、审批、包装、内容投影、结果归一化，且调用/结果要成对落日志。

“插件只能加功能”

不是。插件也能提供策略：审批、沙箱、压缩、上下文注入、turn-stopping，都是插件。

02

Composition

启动装配：profile、bundle 与 patch 层

运行中的 dsh 不是“启动一个 main 函数”，而是从空入口列表开始，按顺序叠加若干层配置，最后得到一棵插件树。理解这棵树，就能回答“某个行为到底是谁装上的”。

2.1三个名词

PROFILE

profile · 一份命名的组合

存在 Harness home（$DSH_HOME/profiles/<name>）。它声明要叠加哪些 bundle、安装哪些树外插件，并持有用户自己的 cordis.patch.yml。

BUNDLE

bundle · 可分发的一层

一个 npm 包，在 package.json 的 dsh.bundle.patch 指向补丁文件。它插入的配置行仍可被上层 patch 覆盖。

PATCH

patch · 按 id 改写

按行 id 定位：替换整行 config（不合并），或插入新行。后应用的层获胜。

出厂 profile 有五个：web、headless、sdk、sdk-minimal、acp。Desktop 保留自己的 desktop profile。选择方式：dsh --profile web 或 dsh web。

Profile叠加的 bundle形态
webdsh-base + dsh-web-app浏览器 UI + HTTP 服务
headlessdsh-base + dsh-headless一次性任务，无服务器
sdkdsh-base + dsh-sdk-appJSON-RPC，供外部进程驱动
acpdsh-base + dsh-acp-appAgent Client Protocol，自动化
sdk-minimaldsh-sdk-minimal（不套 base）刻意精简的独立树

2.2层叠顺序

空入口列表上依次应用：

  1. profile 声明的有序 bundle 补丁；
  2. profile 自己的 cordis.patch.yml；
  3. Harness home 级 patch；
  4. --patch 覆盖层（可重复）。

preset 补丁把同样的优先级规则应用在某个声明的 config.plugins 内部，用来做“每个会话不同的 agent 组合”。

2.4为什么启动必须经过 profile

仓库有一条硬规则：受支持的 Node 应用只能通过命名的 dsh profile 启动。包内 bin、demo、直接 in-process 挂载插件、私有 WebWorker 预览都不算应用启动路径；verify-application-entrypoints 会检查并拒绝绕过 dsh 的 Node 应用入口。

原因不是形式主义：只有经过 profile，插件树、patch 层、HMR、凭据与设置才有唯一的组装点。SDK 也一样——TypeScript SDK 解析同版本的 dsh 依赖并选择 sdk；Python runtime 打包正常的 dsh CLI，客户端默认启动 dsh --profile sdk。

2.5HMR：为什么改了配置就生效

base 默认启用 dsh-hmr，但只监听配置；模块热重载需要显式配置 root（opt-in）。headless、SDK、ACP 关闭 HMR；sdk-minimal 干脆不装。HMR 负责协调文件监听与重载队列，launcher 提供 profile 数据与就绪信号。

实践建议

调试“为什么我的插件没生效”时，按这个顺序查：① --dump-config 里有没有这一行；② 行是否被上层 disabled；③ 依赖服务是否真的激活；④ 注册是否在正确的 scope 上。

03

Core Spine

核心脊柱：六个包与三个事件域

packages/core 是每个组合都会启动的脊柱。它只提供“可替换的骨架”，真正可运行的成品组合在 packages/bundle。先认清六个角色，后面读任何子系统都能挂上去。

包拥有什么ctx key关键事实
core/session append-only 的 SessionEvent 日志与内存存储 ctx.sessions 模型历史由 deriveMessages() 派生，不单独存储
core/system-prompt 提示词段、工具 schema、变量装配 ctx.systemPrompt 装配结果是 system/message 历史节点
core/tools 带作用域的工具注册表与受控执行管线 ctx.tools 准入、守卫、审批、包装、结果改写都在管线里
core/agent Agent 接口、实时注册表、agent/* 事件 ctx.agents 扩展插件依赖它；具体 driver 可替换
core/agent-loop 默认 driver：创建 agent，跑 turn / step 状态机 ctx.agentLoop 注册为 AgentFactory，是公共契约的一个实现
core/scope 按 agent 隔离注册的作用域原语 库，无 ctx key createScope / scopeOf / scopeTarget
llm/llm Message / ContentBlock / StreamChunk 与适配器接缝 ctx.llm prepareCall() 绑定具体适配器与路由

3.1三个事件域，先选对域

仓库把“选哪个事件域”当作大多数改动的第一个决定。判断标准很直接：

DOMAIN 1 · DURABLE

会话事件 session/event

事实必须活过重载时用它。追加进日志，并通过 session/event 广播。典型：turn/start、assistant/message、tool/result。

DOMAIN 2 · LIVE

Agent 事件 agent/*

观察或拦截进行中的工作用它。携带活的 Agent：inbox、step、status、request、validation、continuation。典型：agent/pre-step、agent/request、agent/turn-stopping。

DOMAIN 3 · CAPABILITY

能力事件 fs/*、tools/* 等

给接缝挂策略与适配器，而不 import loop。典型：tools/pre-execute、fs/write-intent、telemetry/*。

一个容易忽略的例外：agent/inbox/spliced 是持久事件，用来让 inbox 在冷读时也能重建待处理消息；其余 agent/* 是实时协调 API。

3.3Agent 与 Loop 的分工

ctx.agents 拥有公共契约：创建、恢复、查询、dispose，以及 Agent 句柄的投递、取消、模型选择。它不知道 step 怎么跑。

ctx.agentLoop 是默认实现，注册为 AgentFactory。它拥有 turn/step 状态机、inbox 认领、请求冻结、工具批次调度。扩展方（UI、hook、工具插件）只 import dsh-agent，因此 loop 可以整体替换。

设计后果

“换 loop”不会牵动工具与会话：ctx.sessions 是独立服务，工具只认 ctx.tools，UI 只消费 session/event 与 agent/*。这是分层带来的真实自由度，不只是宣传语。

3.4作用域：为什么工具能“只给这个会话”

core/scope 是按 agent 隔离注册的原语。插件在自己的 agent.ctx 上注册，贡献只对该 agent 可见；agent 销毁时，作用域随之解开。Agent preset 就是建立在这之上的组合机制：给某个会话换一套工具、提示词或服务实现，而不污染全局。

如果某个服务行要放在 preset 里，它必须声明 isolate realm，否则会与全局实例冲突——这是“按会话换能力”最常见的配置错误。

Lifecycle

一轮对话：turn、step 与两次提交

这是整个仓库最值得慢读的部分。把下面这个动画走三遍，再对照 agent-lifecycle.md 的时序图，你就能回答“模型到底在第几步看到了什么”。

4.1先把两个词钉死

STEP

一次模型请求 + 它请求的工具

一个 step 以 step/start 开始，以 step/end 结束。重试仍属于同一个 step，不会重复装配或重新准入用户消息。

TURN

零个或多个 step 的容器

在认领第一条输入前打开，在“没有欠账”时关闭。被 pre-step 拒绝、输入为空、取消或失败，都可能得到一个没有 step 的 turn。

一句话

turn 负责“这轮要不要干活”，step 负责“这一次请求怎么发”。工具要求继续、或队列里来了新输入，都在同一个 turn 内再开一个 step。

4.3值得停下来想的四个点

① 为什么 prepareCall() 要在提交 prompt 和用户消息之前？

因为绑定适配器、解析推理强度与输出上限都可能是异步的，并且可能失败。把 prepareCall() 放在准入之前，取消或失败时什么都不提交：没有半截 system 节点，也没有半个用户消息。随后用“已备好的调用能力”同步决定提示词如何入历史。

② 系统提示词为什么是历史，而不是请求里的一个字段？

因为“模型看到过什么”必须可重放。装配结果以 system/message 节点进入 surface：第一条占 0 号节点；后续变化按路由能力追加或合并到头部。请求本身只有 header.config、deriveMessages()、header.tools，没有独立的 system 字段。

③ 重试为什么不会重复用户消息？

重试发生在已经打开的 step 内。它复用同一份已渲染的装配结果，重新 prepareCall() 并重新对账系统提示词，但不重复装配、agent/pre-step 或用户准入。失败的尝试以 assistant/attempt 落定，不伪造模型历史。

④ 取消时已经吐出来的文字怎么办？

取消是协作式的。流被取消时，已经交付给用户的前缀会以 assistant/message 且带 interrupted: true 落定，保证下一次请求包含用户真正看到的内容；尚未派发的工具调用补上 ABORTED_BEFORE_DISPATCH 的合成结果。

4.4失败、取消与“未完成的工具调用”

一个 step 失败时，驱动会为每个没有结果的 assistant 工具调用记录错误结果，避免出现“只有 call 没有 result”的悬空历史：

情况合成结果含义
已记录 tool/call，但没有提交结果TOOL_OUTCOME_UNKNOWN可能已经执行，结果不确定
请求失败，且没有该调用的 call 记录TOOL_NOT_STARTED确定未开始
turn 在流式过程中被取消，调用未派发ABORTED_BEFORE_DISPATCH确定未派发

这些结果让后续请求仍能使用成对的工具历史，同时不会自动重试不确定的操作。这是一条安全边界，不是实现细节。

Turn 为什么结束

turn/end 带一个 TurnEndReason：completed、aborted、blocked、error、max-tokens、interrupted、forked。其中后两者只由恢复或分叉构造产生，loop 不会实时发出。

注意

max-tokens 具有传染性：只要 turn 中任意 step 因输出上限被截断，整个 turn 就以 max-tokens 结束，即使后续插件继续了工作。这样消费者能区分“干净结束”和“被截断”。

4.5agent/turn-stopping 是什么

它是 turn 关闭前的串行检查点（没有 next()）。只在自然停止、且队列里没有新的 next-step 输入时触发，给插件一个“最后说一句”的机会：补一条继续指令、做收尾检查、或者什么都不做。

它是 live 事件，不是会话事件；因此它不能用来记录“模型必须看到”的事实——那种事实仍然要落到日志里。

4.6把日志读成故事

假设你拿到一段会话日志，可以按这个顺序还原：

  1. 找 turn/start / turn/end，切出一轮；
  2. 找 step/start / step/end，切出每次模型请求；
  3. 在 step 内，按顺序看 system/message、user/message、request/header，这就是请求前缀；
  4. 看 assistant/message（或其内嵌 stream）与 tool/call / tool/result 配对；
  5. 最后用 deriveMessages() 的规则得到模型历史——注意 surface 可能被压缩事件替换过。

05

Tool Execution

工具：一条受控执行管线

模型说“调用 bash”，离真正 spawn 一个进程还隔着准入、守卫、审批、包装、内容投影与结果归一化。理解这条管线，就理解了 dsh 如何在不改 loop 的前提下加策略。

5.1工具是什么

工具是注册在 ctx.tools 上的 ToolDefinition：名称、描述、JSON Schema 参数，以及一个 execute() 主体。它还可能声明执行模式、内容投影、结果收尾、UI 呈现等能力。

// 概念示意，字段以 docs/subsystems/tools.md 为准
interface ToolDefinition {
  name: string
  description: string
  parameters: JsonSchema        // 受限的 JSON Schema 子集
  executionMode?: 'parallel' | 'exclusive'
  execute(input, ctx): Promise<ToolResult>
  projectContent?(...)          // 执行准备的内容
  finalizeContent?(...)         // 最后一道内容不变量
  presentCall? / presentResult? // UI 呈现
}

工具注册表是带作用域的：一个 agent 可以通过自己的 agent.ctx 注册只属于它的工具；ToolRestriction 则是对继承来的工具集合做实时过滤。于是“同一个会话里突然多了一把工具”是正常现象——step 开始时才决定这一步准入哪些 schema。

执行模式

EXCLUSIVE

独占，形成顺序屏障

单独运行，前后的调用不能越过它。适合有全局副作用、必须串行的操作。

PARALLEL

并行，滚动池

并行安全调用进入有界滚动池，默认每个 step 最多 10 个在飞（DEFAULT_MAX_PARALLEL_TOOL_CALLS）。

loop 把完整的原始调用批次交给 ctx.tools.execute()，由执行器保留模型顺序的结果、屏障语义与取消传播。启动前还会重新分类一次，因为前面的调用可能改变了后面的执行条件。

5.3七个容易忽略的规则

  1. tool/call 在执行前落日志。 这样即使进程崩溃，也能知道模型请求过什么；结果缺失时由恢复逻辑补合成结果。
  2. 审批是“一次性”的。 审批缺失或无法回答时默认拒绝，而不是默认放行。
  3. 守卫是单调的。 已注册的守卫只能拒绝或弃权，不能把别人的拒绝改回允许；身份相关策略因此不可被后续插件重排。
  4. 包装器只包执行。 超时、重试、指标这类 around-dispatch 关注点挂在 tools/execute 上，不需要改工具主体。
  5. 结果归一化不等于吞错。 管线快照候选结果；快照或投影抛错会变成 isError 的结果，而不是让整个 step 消失。
  6. 附加上下文有顺序。 活跃批次里的 additionalContexts 按 FIFO，在记录完工具结果之后注入为 user/message，保持 call/result 相邻。
  7. 拒绝也要有结果。 被拒绝的调用仍会产生 tool/result，模型能读到拒绝原因，而不是面对一段无回应的历史。

5.4写一个工具，最小检查单

MUST

契约

名称稳定、描述从模型视角写、参数在受限 schema 子集内、结果有明确上限（字节 / 条目）、错误用结构化失败。工具不读 UI 词汇。

MUST

生命周期

通过 ctx.tools.register() 注册并返回 disposer；不要模块级单例；需要按 agent 隔离时用 agent.ctx。

SHOULD

呈现

如果需要专门的卡片，设计 presentCall / presentResult，并保证 Host presenter 是纯函数、Web 卡片可从原始事件与结果元数据重建。

SHOULD

证据

为拒绝路径写测试：从执行器进入，证明策略真的拦住了，而不是仅在 UI 上隐藏。产品可见插件还需要一次真实组合测试。

完整步骤见 docs/cookbook/adding-a-tool.md；工具类型与事件签名见 docs/subsystems/tools.md。

5.5PTC：把工具编排变成代码

PTC（programmatic tool calling）模式把保留的 run_code 传输和它的有序子调用一起送进同一条管线。子调用携带父 token，记录 tool/ptc-dispatch；拒绝作为绑定失败返回；子调用省略 additionalContexts，以保持 call/result 相邻。

它示范了一件事：新执行形态不需要改 loop 或工具定义，只需要一个新的 ToolExecutor 与执行接缝。

自检问题

“如果我的策略只在工具内部实现，另一个直接调用 execute() 的路径能不能绕过？” 能，就说明策略放错了层。仓库规则要求：在做出决定的那次操作里执行决定，而不是靠 schema 省略、提示词过滤或监听器顺序。

06

Session Log

会话：日志、surface 与投影

如果只能读一个子系统，读会话。它是模型历史的唯一真相来源，也是恢复、分叉、标题、反馈、检索、遥测的共同基底。

6.1一条事件长什么样

日志是 append-only 的 SessionEvent 序列，序号连续，内容是 lossless JSON。消息型事件还要带 surface 元数据，说明它如何进入有序的模型可见面。

ENVELOPE

信封字段

seq、type、data、可选的 surfaceOp / sourceEventSeqs、以及兼容标记 ignorable。非消息事件不得携带 surface 元数据。

SURFACE

五种消息型事件

system/message、developer/message、user/message、assistant/message、tool/result。只有它们能出现在 surface 上。

6.2deriveMessages：日志 → 模型历史

投影规则很克制，但每一条都有原因：

事件进入模型历史？说明
user/message是原样携带 content；人工输入、注入上下文、目标续轮都由 source 区分
assistant/message是（内容非空时）内嵌精确的紧凑 stream，作为重放、用量与 UI 证据，不再变成第二条消息
assistant/attempt否保留失败 / 重试 / 取消 / 流错误的尝试，不伪造历史
tool/result是一等公民的 tool 角色消息，带 tool call 身份
turn/*、step/*否结构性事实
插件自有事件视声明需要改历史内容时必须注册纯 SessionMessageProjection
为什么强调“纯”

消息投影是纯函数：给定事件与之前的消息，返回不可变的新消息映射。这样同一段日志在任何读取端（在线、离线、冷读、导出）都能得到同样结果；卸载一个被使用的投影定义，会阻止缓存读取，而不是悄悄给出不同答案。

6.3Surface 替换：压缩为什么不是“删历史”

压缩不是把旧事件删掉，而是追加一个带 { op: 'replace', startSeq, endSeq } 的事件，遮住一段 surface 节点。原始事件仍在日志里，所以：

  • 人类可读的 transcript 读的是“追加来源”的事件，能看到完整过程；
  • 模型历史读的是 surface，看到的是摘要加后续内容；
  • 重放与审计仍然完整。

这就是“一份日志，两种投影”的具体含义。

6.4持久化：generation 与迁移

落盘由 ctx.sessionPersistence 接缝负责，默认 JSONL 后端。几个硬约束：

  • JSONL v0 用 session.jsonl[.zstd]；v1 及以后用 session.vN.jsonl[.zstd]。
  • 已提交的 generation 文件永不重命名、覆盖或删除。
  • stat / list 只读头部，选择编号最高的规范 generation，必要时翻译历史头部。
  • 写打开时，先编码、校验，再以独占方式发布新的版本命名后继文件；源文件保持原样。
  • 每个相邻迁移包只负责一个 vN → vN+1 步骤。

未封口的尾部修复属于句柄消费者的职责；迁移只会为“已发布版本中、被后续 turn/start 封住的有限重启场景”补一个缺失的 turn/end。

6.5投影接缝：UI 状态不要自己扫日志

ctx.sessionProjections 注册“折叠单元”，增量消费已提交事件；载体（carrier）把裁剪后的客户端视图按批 snapshot() 出去。领域服务在激活期等待注册、持有私有句柄，对外只暴露业务方法。

规则很实用：释放注册会移除全局参与，但已持有的句柄仍能继续折叠。这让插件卸载与正在进行的会话读取可以安全重叠。

6.6为什么模型可见就必须落日志

把所有推论摊开看：

恢复

崩溃后能重建同一份历史；没有第二条隐藏状态。

分叉

在任意稳定边界切出子会话，种子事件深拷贝，子会话独立演进。

可审计

导出、回放、快照测试都从同一份事实出发。

因此，新增一个“会进入模型请求”的输入，就必须新增会话事件；新增一个“会改变已有消息内容”的插件，就必须注册消息投影。这不是文档建议，而是仓库的合并门槛。

07

Capability Seams

能力接缝：定义、提供者、消费者

dsh 里最常被误用的词是“接缝（seam）”。它不是一个抽象类，也不是任何可配置项，而是三种角色齐备的可替换能力。

7.1三角色，缺一不可

ROLE 1

Service Definition

声明接口与生命周期契约的包，例如 dsh-fs、dsh-llm、dsh-subagents。它不包含具体实现。

ROLE 2

Service Provider

实现接口并注册到同一 ctx key 的包，例如 fs-local、fs-ssh、llm-deepseek。

ROLE 3

Consumer

只依赖定义、通过服务调用能力的包，通常是模型可见工具，例如 tool-fs、tool-bash。

一个包可以兼任多个角色，但只占一个角色不构成接缝。新增能力时，必须同时设计三者；否则你得到的只是一个“大家都 import 的实现”。

7.2为什么这很重要：换一个提供者，换一个世界

文件系统与子进程提供者共享同一个执行世界。把它们同时指向远程沙箱，Bash、PTY、LSP 会一起搬过去，不需要为每个工具 fork 一份实现。

子代理提供者同理：同一接口后面可以是新开的子 agent、另一个产品的委托回合、Codex/Claude Code 进程，甚至 SDK 会话。

7.4设计接缝时的四条纪律

  1. 为所有现有消费者设计定义。 工具 schema、Loader、UI、传输、提供者特有行为都留在消费者或提供者里，别让一个消费者决定服务契约。
  2. 反向信号也要认。 一个只有一个内部调用者的公共方法，往往应该退回私有能力闭包，而不是上升为服务 API。
  3. 提供者不泄漏。 扩展插件依赖定义；组合 bundle 才可以依赖脊柱插件。
  4. 可选服务用 ctx.get(name)。 ctx.<name> 的属性代理对拓扑敏感，只用于已声明的注入。

8.4两种典型改动的完整路径

CASE A

给模型加一个能力

定义 ToolDefinition → 在插件 apply 里注册 → 配置 schema → 设计结果上限与失败 → 写执行器级拒绝测试 → 需要时加 UI presenter → 更新包 README 的 Model Experience 段。

CASE B

换一种执行环境

实现 Service Definition（fs / subprocess / sandbox）→ 在 bundle 里替换提供者行 → 确保消费者不 import 具体实现 → 用同一套工具跑一次真实组合测试 → 检查权限与写根。

8.5不要做的事

  • 不要新增全局 current / active / selection 单例；共享状态挂在服务或实例上。
  • 不要让运行时、控制器、网关承载业务分支；业务规则留在自己的包里，通过注册面接入。
  • 不要在提示词、工具 schema、结果里出现 UI / 传输 / 实现词汇；从模型视角写契约。
  • 不要用 schema 省略或提示词过滤来“执行”一个决定；直接或替代调用者能绕过，就不算执行。
09

Hosts & Protocols

宿主：Web、Desktop、SDK 与 ACP

同一套 Host 服务，可以出现在浏览器、Electron 窗口、一次性 CLI、JSON-RPC 服务器或 ACP 自动化里。差别在“载体”，不在 agent 本身。

9.1Host 与 Client 的分工

HOST

拥有能力与副作用

文件系统、进程、终端、凭据、会话写路径、模型调用、插件管理。Host 上的 API 控制器把业务能力投影成 Remote 方法。

CLIENT

拥有界面与交互状态

浏览器里的 React 客户端：连接、对象服务、槽位、ui-* 插件、会话卡片。它通过认证传输读取事件、调用命令。

两端之间的桥是 ctx.connection（认证的浏览器传输）与 ctx.typertGateway（把生成的 Remote 描述绑定到活的 Cordis 服务）。ctx.remoteAccess 决定非 owner 的 peer 能调用哪些方法，并按业务注册的角色策略过滤列表、推送访问快照。

9.2四种载体

载体启动方式特点
Web dsh web（默认 127.0.0.1:3080） Host 提供 HTTP 与静态前端；本机启动会打开浏览器，SSH 启动只打印宿主 URL
Desktop dsh desktop / 打包应用 Electron 启动私有 Desktop Host，调用共享 CLI profile runner；默认 OS 分配端口
Headless dsh headless "task" 无服务器，一次任务后退出；适合脚本与 CI

9.3Desktop 的关键设计

Desktop 不是“把 Web 塞进壳”这么简单：

  • 它携带完全一致的 dsh 生产运行时（签名资源内），并独占 $DSH_HOME/profiles/desktop。
  • Electron 以 Node 模式启动私有 Desktop Host；Host 调用共享 CLI profile runner 和完整 Web 应用。
  • 窗口先加载打包好的 Web 资源，等 boot injection 就绪后再激活 client 插件——所以首屏不依赖 Host 先启动完。
  • Web 拥有 RPC 与流；desktop carrier 把本地页面接到已认证的 Host。Node IPC 承载 boot injection、就绪、致命错误与关闭。
  • Desktop 与 npm CLI 共享产品数据，但包、激活与 lockfile 分开；桌面自带的 CLI 管理它初始化过的插件。

9.4SDK：把 loop 投影到进程外

TypeScript SDK 解析同版本的 dsh 依赖并选择 sdk profile；Python runtime 打包正常的 dsh CLI 为平台轮子，客户端默认启动 dsh --profile sdk，并显式指定 Harness home。两边都只暴露 profile 选择与有序 patch 文件，不暴露任意 Cordis 树。

重要

仓库规则要求：agent-loop、会话生命周期、SessionEventMap 的变化，必须在同一个 PR 里更新 TypeScript 与 Python SDK 的期望输出。pnpm run test 不覆盖这两个面，别以为绿了就完了。

9.5UI 也是插件图

Web 客户端有自己的插件模块图（ctx.clientModules）。会话里的每一种新节点，都通过 ConversationNodeDefinition + 键渲染器接入；工具卡片从原始事件与持久化结果元数据推导，Host presenter 保持纯函数。

产品文案受 locale 约束：客户端可见文本走类型化字典与 t，verify-client-ui-i18n 会拒绝硬编码文案。

工程：命令、测试与阅读顺序

这个仓库的工程约束和架构是同一套思路：边界显式、失败要响、证据类型要匹配改动面。先跑起来，再学会用最小的检查覆盖你的改动。

10.1跑起来

# 环境：Node >= 24.9，pnpm workspaces
pnpm install

# 从源码构建并启动 Web（构建 + 启动 + 客户端热更新）
pnpm run dev:web

# 桌面
pnpm run dev:desktop

# 一次性任务（需要 DEEPSEEK_API_KEY，可放在根目录 .env）
pnpm dsh --profile headless "解释一下这个仓库的 turn 生命周期"

# 看最终装配树
pnpm dsh --profile web --dump-config

Make 入口：make web、make dev-web、make desktop、make build；ARGS= 可转发选项。

10.2构建的两个平面

仓库严格区分源码平面与产物平面：静态检查与测试通过 tsconfig paths 解析到 src，在干净树上就能通过；消费 lib/ 的检查必须显式声明依赖。

ARTIFACTS

pnpm run build:artifacts

tsc 产出 lib/types，tsdown 打包运行时与 Web。日常开发用它。

CHECK

pnpm run build:check

针对当前产物，typecheck 聚合测试与脚本。声称完成前，必须在最新 artifacts 之后跑一次。

10.3测试阶梯：用对的证据

命令回答什么问题什么时候用
pnpm run test单元行为是否成立改了一个包内部逻辑
pnpm run test:coverageCI 覆盖率门槛（每文件 100%）不是日常默认，CI 拥有该信号
pnpm run test:e2e真实 API 下的端到端改 provider、模型调用路径
pnpm run test:snapshot无密钥回放已录制会话，跑过出厂 profile模型可见或产品可见变化
pnpm run test:expectedowner-local 进程期望本地特定进程行为
pnpm run typecheck类型面任何改动
pnpm run lint / duplication风格与克隆检测提交前
pnpm run doc-sync / test:docs文档链接、预算、生成物新鲜度改文档或生成目录
别默认全套

仓库明确要求：证据要匹配改动面，不要反射式跑全套，也不要在提交/推送时重复已通过的检查。CI 拥有穷尽覆盖与平台矩阵；本地只跑能覆盖这次 diff 的最小集合。只有明确要求、诊断 CI 或不可约的全局改动，才全量跑。

10.4快照测试的心智模型

快照不是“截图”，而是把一次真实会话（模型调用被录制/回放）跑过出厂 profile，断言最终产物。无密钥时自动跳过真实 API；test:snapshot 用录制数据重放。

  • 顶层的 snapshots/ 只放会话驱动用例；其他期望输出留在 owner 本地。
  • fixture 在 macOS / Linux 上回放；坏了修 fixture，不要修 normalizer。
  • 录制用 pnpm run test:snapshot:record（需要 key）。

10.5约定速查

模块

全 ESM；跨包用包名，本地相对导入带 .ts；函数插件具名导出 name/inject/Config/apply，不默认导出。

类型

strict；剩余 any 必须解释；不新增 as unknown；不透明 id 用 Branded<B>。

事件

声明合并；JSDoc 标 @mode 与 payload @param；waterfall 必须 next()；闭合联合以 assertNever 收尾。

错误

类型化、结构化失败；空 catch 必须命名错误与原因；让依赖工作停下并可见地报告未知状态。

配置

部署差异必须是经校验的 Config 字段；插件里不写死 tunable；DEFAULT_* 不是可配置性。

文档

每段一行（软换行）；代码变化同 PR 更新 README/JSDoc；架构变化更新 docs/architecture.md。

10.6调试一条真实链路

  1. 装配层：dsh --profile web --dump-config，确认行、config、disabled。
  2. 服务层：确认插件真的激活（依赖缺失会静默等待），用 ctx.get() 判断可选服务。
  3. 会话层：找到 $DSH_HOME 下的 session 目录，看 session.vN.jsonl；按 turn/step 切段。
  4. 请求层：看 request/header 与 deriveMessages() 的结果；注意 surface 替换。
  5. 流层：assistant/message 内嵌 stream 是精确证据；失败尝试看 assistant/attempt。
  6. 工具层：call/result 成对检查；拒绝与异常都应留下结果。

10.7五个渐进练习

EX 1 · 30 MIN

读一次日志

随便开一个会话，跑一轮带工具的对话，在 JSONL 里标出 turn/step 边界与 request 前缀。

EX 2 · 1 H

替换一个提供者

用 --patch 把 llm-deepseek 换成 llm-replay，观察哪些行变了、哪些消费者没变。

EX 3 · 2 H

写一个只读工具

注册一个返回固定 JSON 的工具，验证 schema 准入、结果上限与 UI 卡片。

EX 4 · 3 H

加一层策略

用 tools/pre-execute 拒绝某个参数模式，写执行器级测试证明无法绕过。

EX 5 · 1 D

做一个会话投影

从事件流折叠一个小状态（例如每轮工具计数），供 UI 读取，并验证释放注册后的行为。

EX 6 · 2 D

换执行世界

把 fs/subprocess/sandbox 同时指向 SSH 或沙箱，跑同一套 Bash/Read 工具，记录差异。

Reference

术语、测验与延伸阅读

12.1术语表

Turn /tɜːrn/
一轮对话的容器，可含零个或多个 step。认领输入前打开，没有欠账时关闭，以 turn/end 和结束原因收尾。
Step one model request
一次模型请求加上它请求的工具执行。以 step/start / step/end 界定；重试不另开 step。
Surface model-visible history
由消息型事件组成的有序面。每个节点声明 append 或 replace；deriveMessages() 折出模型历史。压缩通过 replace 遮蔽旧节点，不删除日志。
Durable event session event
写进会话日志、可重放、可迁移的事实。新增模型可见输入时必须新增这类事件。
Live event agent/*
进程内广播的协调/状态事件，携带活的 Agent；不承担恢复。例外：agent/inbox/spliced 是持久投影事件。
Waterfall
around-middleware 式派发：监听器收到 next，调用它委托下游，不调用则短路。适用于请求、pre-step、工具策略。
Effect
Cordis 的可回滚注册单元。通过 ctx.effect() / ctx.on() 安装，插件卸载时自动释放。
Projection
从已提交事件增量折叠出的派生状态。会话投影服务 ctx.sessionProjections 统一注册与快照。
Seam capability seam
三角色齐备的可替换能力：Service Definition、Service Provider、Consumer。缺一个角色就不是接缝。
Profile / Bundle / Patch
profile 是命名的组合；bundle 是可分发的一层配置+代码；patch 按行 id 替换或插入。后应用者获胜。
Preset
按会话组合 agent 的机制，补丁应用在声明的 config.plugins 内，优先级规则与全局层叠一致。
Scope
按 agent 隔离注册的原语。经 agent.ctx 注册的贡献只对该 agent 可见。
Generation
持久化文件的版本命名（session.vN.jsonl）。已提交的文件不可改名、覆盖或删除；读写选择最高版本。
PTC
Programmatic Tool Calling：模型写代码编排工具调用，子调用仍走同一条受控管线，并保留父子关系日志。
ACP
Agent Client Protocol，自动化专用服务器，通过 JSON-RPC stdio 驱动 agent。
Remote / Typert
Host 能力投影到客户端的方法与类型图。Gateway 把生成的描述绑定到活服务，RemoteAccess 做方法级授权。
Compaction
上下文压缩接缝。basic 提供者用压力触发与摘要；工具结果剪枝与图片卸载是独立插件。
Spill
把超大工具输出落到存储接缝，模型看到引用而非全文；策略由 spill-policy 决定。
Deliverable
一轮结束时显式交付的文件，以及记录的 workspace 变更摘要。
Hook
外部命令钩子桥（Claude Code / Codex 兼容），以 hook/invoked / hook/result 落为仅日志事件。
