AI 项目重点

1. alibaba/open-code-review

语言与热度：Go；36,974 Stars；本周 +14,144。

解决的问题：通用智能体审查大变更时，容易漏文件、评论位置漂移，规则执行不稳定。

核心亮点：工程管线负责选文件、关联文件分组和规则匹配；Agent 负责查找上下文、动态判断，再输出行级评论。也支持对完整文件执行 ocr scan。

适用人群与场景：维护多人代码库的工程师和评审负责人，可先在一个真实 PR 或陌生目录的审计任务中验证命中率与误报。

项目 README 的自有基准强调精确率、F1、耗时和 token 效率，但同时明确召回率低于通用智能体。这是一项主动取舍，不应将项目指标外推到你的仓库；接入还需要 Git 与模型端点配置。

3. ayghri/i-have-adhd

语言与热度：Python；48,294 Stars；本周 +7,869。

解决的问题：编码助手把结论埋在铺垫和旁枝里，实际下一步不够醒目。

核心亮点：规则要求先给动作、多步任务编号、控制旁枝，并以一个具体下一步结尾。

适用人群与场景：高频阅读智能体回报的开发者，可用于故障处理、代码评审结论和移动端快速决策。

它改善的是交付结构，并不保证建议正确。仍需用测试和源码验证技术判断。

4. affaan-m/ECC

语言与热度：JavaScript；262,300 Stars；本周 +5,877。

解决的问题：单次提示词难以维持长期项目的计划、测试、评审、记忆与安全检查。

核心亮点：把技能、Agent、钩子、规则与安全扫描组织成可复用的工程流程。

适用人群与场景：已有智能体开发流程的团队，可先选一条测试或评审链路试用，再决定是否接入整套系统。

README 标明各平台支持程度不同；不要仅凭“支持 Codex、Claude Code 等”推断所有功能完全一致。

5. stablyai/orca

语言与热度：TypeScript；72,147 Stars；本周 +5,272。

解决的问题：多个编码智能体同时工作时，任务、上下文和代码改动容易互相干扰。

核心亮点：桌面工作台使用隔离的 Git 工作树并行运行，允许比较结果；还提供远程运行、差异评论和移动端跟进能力。

适用人群与场景：同时试验多种实现方案的工程师，可从一项可比较的任务和少量工作树开始。

并行不等于可以直接合并。结果比较、冲突处理和最终测试仍应由人负责。

其他热门项目

2. bilawalsidhu/gods-eye-view

语言与热度：JavaScript；38,037 Stars；本周 +11,683。

解决的问题：航班、船舶、卫星、地震和公共摄像头等公开信号分散，缺少统一的空间探索界面。

核心亮点：在浏览器里的三维地球叠加不同数据层，支持对象追踪与可选的语音交互。基础数据源可先体验，高阶图层需要额外配置。

适用人群与场景：地理信息、数据可视化与交互原型开发者，可用于公开信号教学和空间界面实验。

README 说明道路交通是基于真实道路的模拟，摄像头朝向与火箭轨迹包含粗略估计；不能把画面中所有内容当成实时事实。

本周最值得看

open-code-review 值得拆开看，因为它没有把所有审查步骤都交给模型。文件选择、分组、规则匹配、评论定位适合程序化约束；需要理解上下文与判断风险的环节才交给 Agent。这样做的价值是让评审结果更容易复查，而非承诺“自动审查不会漏掉问题”。

Open Code Review 以读取变更、规则匹配、Agent 深审、行级反馈组成审查流程

最小试用方式是选一个已知缺陷和误报样本的 PR，对照现有人工评审结果，看它是否找对文件、评论是否落在正确行、漏掉了哪些问题。不要只看它生成多少条评论。

趋势观察

审查从提示词走向工程约束：第一名让模型负责动态判断，但把覆盖范围和定位交给确定性管线。

协作工具开始承接生成后的工作：orca 管理隔离工作树，ECC 管理过程规则；二者都不能代替最终验证。

表达方式也在被产品化：i-have-adhd 的热度说明“先说结论”能直接改善日常使用。

界面越震撼，越要核对数据边界：gods-eye-view 的实时源与模拟层并存，README 的说明应和演示一起读。
