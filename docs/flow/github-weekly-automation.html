一篇 GitHub 周报，如何自动从榜单走到读者面前？

每周五 18:00，系统从 GitHub Trending Weekly 开始，完成选题、核验、配图、Hexo 构建和微信公众号草稿。机器负责重复工作，质量门槛负责决定能不能继续。

每周五 18:00（北京时间） GitHub Trending Weekly 博客 + 微信草稿 不自动发布 / 不群发

先看结论

这不是一个“按按钮写文章”的脚本，而是一条有输入、有输出、有质检、有止损的内容流水线。

机器把原料整理成可审阅的成品

它读取榜单，找出本周主线，制作“总览到分项”的阅读路径，再分别输出博客封面、微信封面、TOP 5 摘要海报和正文信息图。最终发布前仍保留人工判断。

主流程：从榜单到草稿

每一步都产出下一步需要的结果；关键检查失败，就在当前节点停止。

01 / TRIGGER

定时触发

每周五 18:00，在本地项目目录启动任务。

02 / RESEARCH

抓取与核验

读取 Weekly 榜单，校验项目、链接、语言和 Star。

03 / EDIT

提炼主线

形成一句核心判断，选出 TOP 5 和逐项目分析。

04 / VISUAL

生成视觉

为博客、微信和正文分别排版，年份必须可见。

05 / PUBLISH

写入与上传

图片上传 OSS，写入 Hexo Markdown 与微信 HTML。

06 / QA

质量门槛

检查 readiness、图片、移动端可读性和构建。

07 / OUTPUT

提交与草稿

push 博客，创建微信草稿，记录 media_id 和状态。

四层协作，不互相越界

总控 Skill 负责编排，底层工具各自完成擅长的事情。

01 · DATA

数据层

读取 GitHub Trending Weekly，保留能验证的项目、链接、语言、总 Star 和本周新增 Star。

02 · EDIT

编辑层

把榜单变成观点：一句核心判断、TOP 5、项目价值、适用人群与落地场景。

03 · VISUAL

视觉层

统一暖白、黑字、GitHub 绿和橙红重点；底图与准确文字分开生成。

04 · DELIVERY

发布层

Hexo 负责博客，md2wechat 负责排版，baoyu 负责创建草稿，PicGo 负责 OSS。

视觉系统：先给全貌，再带读者下钻

这是 GitHub 周报的专属能力

项目列表、排名、Star 数、TOP 5 海报和这套“总览到分项”的阅读路径，只在每周 GitHub 趋势系列启用。其他博客按照自己的主题选择封面、配图和文章结构，不会被强行套用。

微信公众号 Skill 怎么接上来？

博客与公众号共用内容判断，但不共用网页渲染方式。

总控：wechat-article-generator

负责调研、写作、图片规划、质量门槛和整个流程的编排。

排版：md2wechat

负责主题发现、inspect、预览和生成微信兼容 HTML。

发布：baoyu-post-to-wechat

负责上传微信图片、封面素材和创建草稿，不自动群发。

托管：PicGo / OSS

博客 Markdown 只使用真实 OSS URL，上传失败就停止。

状态：state.json

保存哈希、图片和 media_id，重试时避免重复创建草稿。

合集：每周 GitHub

当前能创建草稿；如果没有可验证的 album_id，就报告待后台归档。

可靠的关键，是知道什么时候停

自动化不追求“无论如何发出去”，而是把错误拦在发布之前。

数据不可信不编造 Star，不把 Daily 快照冒充 Weekly 历史。
图片不一致日期、年份、项目名或 Star 与文章不一致，就重新生成。
OSS 失败不提交本地图片路径，不回退到无关默认封面。
微信 readiness 失败缺封面、凭据、主题或 IP 白名单时，不创建草稿。
构建失败Hexo 或仓库审计未通过，就不 push。
合集无证据没有 album_id 或后台操作证据，就不报告已归档。

给读者的一句话版本

如果只想快速理解这套系统，可以记住下面这句话。

它到底做什么？

每周五，系统把 GitHub 热榜整理成一篇“先看全貌、再读重点”的周报：先列出项目和 Star，再解释主线项目为什么值得关注，最后分别生成博客和公众号版本。

它为什么不直接发布？

因为数据、图片、平台审核和合集归档都可能出问题。系统负责把内容准备成可审阅草稿，真正发布前保留一次人工确认。
