DeepSeek Harness 学习手册：从 363 个包里找到一条主线

我把 DeepSeek Harness 的 363 个工作区包收成一份 15 节的手册：先建心智模型，再顺着一次 turn 读源码，最后用能力接缝判断新行为该放哪。

读 dsh 源码最难的，不是看不懂某个文件，而是不知道下一个该打开哪个文件。

我第一次打开 packages/ 时，看到 52 个分组、363 个工作区包。每个包都有自己的 README，每份 README 都写得挺清楚，但我读完第三章就忘了第一章。

问题不在于文档少，而在于它们平铺。我需要的是一条主路径：先看什么、后看什么、什么时候可以跳过。

于是我给自己写了一份交互式手册（learn-harness/index.html，13 章正文加 2 篇附录）。它不是 API 文档的复述，而是一张阅读地图。这篇文章记录手册里的主线，以及我按这条线读完之后的几个判断。

一句话看懂：dsh 的一切都是插件；一次对话是 turn 里的若干 step；模型看到的上下文，永远是会话日志投影出来的。

手册本身是个单页应用，能搜包名、能点开每个包的说明、能按主路径高亮，读起来比 Markdown 顺手。我把它和这篇文章放在同一个域名下，点开就能用：

一、363 个包，不是用来通读的

先把数字摆清楚，因为它决定了读法。

dsh 仓库里 packages/ 下有 52 个分组、363 个工作区包。出厂 profile 有 5 个：web、headless、sdk、sdk-minimal、acp。会话格式版本是 SESSION_FORMAT_VERSION = 4。

这些数字放在一起说明一件事：包的数量不是知识量，而是组装方式的数量。

同一个能力可以出现在多个 profile 里，以不同配置、不同宿主、不同沙箱策略出现。你要理解的不是 363 份代码，而是它们怎么被拼起来，以及主路径上谁先谁后。

所以手册的第一条规则是：先读装配，再读主干，最后才按需展开分支。

二、第一个心智模型：一切皆插件

dsh 跑在 Cordis 上。Cordis 的世界观很简单：插件往共享的 ctx 上贡献服务、类型化事件和可逆的副作用。

这里有两个词值得停一下。

可逆：注册即副作用。插件卸载时，它注册的东西会跟着回滚，不需要谁去手动清理。这解释了一个常见困惑——为什么改配置就能换掉模型适配器，而不是去改某个 if。

没有特权内核：模型适配器、工具注册表、会话日志、agent loop，全都是插件。没有一处”必须改这里”的补丁点。想加行为，就在旁边挂一个插件。

我一开始把这理解成”架构优雅”，后来发现它更实际的作用是：它规定了新代码该写在哪。凡是能写成插件的行为，就不该动 loop。

三、装配：从空上下文到 web 应用

一个正在运行的 dsh，是启动时按顺序叠出来的插件树。

叠的顺序是：profile 列出它要用的 bundle 顺序，bundle 带着自己的配置行和代码，最后由用户的 cordis.patch.yml 按行 id 覆盖 config，或者插入新行。

我建议第一次读的时候，只盯住两件事：

  1. 第 4 层的 patch 是按 id 覆盖的，不是按位置。所以你能改一行而不影响其它行。
  2. 层是叠加的，不是替换的。上层没提到的行，仍然保留下层的配置。

理解这两点之后，”为什么我改了配置没生效”这类问题就有了解法：先确认你改的是不是同一行 id，再确认有没有更上层把它盖回去。

四、核心脊柱：六个包

抛开宿主和外围，真正要读的是六个包，各自挂一个 ctx key：

包负责什么ctx key
core/session追加式的会话事件日志与内存存储ctx.sessions
core/system-promptprompt 分段与工具 schema 组装ctx.systemPrompt
core/tools作用域内的工具注册表与受控执行管线ctx.tools
core/agentAgent 接口、活动注册表、agent/* 事件ctx.agents
core/agent-loop实现该接口的默认驱动器ctx.agentLoop
llm/llm消息与流式词汇，以及适配器接缝ctx.llm

core/scope 也在脊柱上，但它提供的是库，不挂 key。

这六个包之所以叫脊柱，是因为它们串起了所有其它能力：工具要经过 ctx.tools，模型要经过 ctx.llm，历史要从 ctx.sessions 投影，prompt 要由 ctx.systemPrompt 组装。

剩下的三百多个包，绝大多数是在这条脊柱上挂东西。

五、一轮对话：两次提交

这是手册里我改得最多的一章，也是最值得慢慢读的一章。

先对齐定义：step 是一次模型请求加上它调用的工具；turn 是零个或多个 step。turn 在认领第一个输入之前打开，在没有欠账时关闭。

完整走一遍：

  1. turn/start：认领下一步输入，顺带一条排队消息。
  2. 快照会话的模型选择，组装 prompt 分段和被允许的工具 schema。
  3. agent/pre-step：监听者可以接受、改写或拒绝。拒绝，或者第一条就被改写成空，这个 turn 直接关闭，一步都不走。
  4. step/start，然后 agent/request 进入 prepareCall()。
  5. prepareCall() 绑定适配器之后，才提交 system prompt 和被接受的用户消息。
  6. 从日志里推导并冻结模型历史，开始流式请求。
  7. assistant/message 落盘，接着 tool/call* 走工具管线。
  8. step/end。如果工具还欠一次请求，或者又来了新输入，就再走一步。
  9. 欠账清零，turn/end。

我最初以为”提交”是循环结束时的统一动作。实际上是两次提交：输入在绑定适配器后立刻提交，结果在流式结束后提交。

这个顺序不是洁癖。它保证了一个很难得的行为：取消时，system prompt 和用户消息一个都不提交。半截状态不会进入日志，下次恢复不用猜。

六、工具是一条受控管线

工具调用看起来像”模型说一句话，函数跑一遍”。在 dsh 里它是一条有四个位置的管线：

tools/pre-execute → tools/execute → tools/post-execute → tool/result

pre 管准入和改写，execute 是真正的执行，post 处理结果，最后 tool/result 落进日志。中间几个是 waterfall，监听者必须调用 next() 才会继续往下走——不调用就是短路。

还有一个细节容易被忽略：失败的 step 会把缺失的工具结果记下来。这样日志里不会出现”发起过但没结果”的空洞。

我读完这一章的实际收获，是明白了权限、沙箱、超时这些策略该挂在哪：不是塞进工具实现里，而是挂在 pre 上。

七、会话日志才是事实源

dsh 里有一句话：模型可见，就意味着已记录。

模型的上下文不是内存里攒出来的数组，而是 deriveMessages() 从会话日志投影出来的。每个 assistant/message 内嵌产生它的完整流式记录；assistant/attempt 保留失败、重试、取消和流错误的尝试，但不进入模型历史。

这条规则带来两个后果。

第一，你不能”只在内存里加一点上下文”。任何进入模型请求的东西，都得先在日志里有一个事件。

第二，格式变更很贵。SESSION_FORMAT_VERSION 现在是 4，提交过的代际不会被移动、覆盖或删除。要做变更只能新增一个带版本名的后继格式，走一次相邻迁移。

我原先以为这是保守，后来懂了：会话是用户资产的载体，删掉一代就等于删掉别人的历史。

八、能力接缝：三个角色才算完整

原文对”接缝”（seam）的定义是三段式：Service Definition 声明接口，Service Provider 实现它，Consumer 使用它。一个包可以同时扮演多个角色，但只有一个角色不算接缝。

这是我在手册里最有获得感的一节，因为它能直接判断”这个改动是不是做全了”。

举个真实的例子：文件系统和子进程的提供者共享同一个执行世界。所以当你把它们一起指向远程沙箱时，Bash、PTY、LSP 会跟着一起搬过去，不需要为每个工具写一份远程分支。

也就是说，换一个提供者，改变的是整个产品，而不是某个函数。

判断新能力时，我会问三句：接口在哪、谁实现、谁用。三句都有答案，才算设计完。

九、扩展时把新行为放对位置

事件是扩展点，第一件事是选对事件域。手册里把域分成三类：

  • 会话事件：追加进日志的持久事实。需要跨重载活下来，就用它。
  • agent 事件（agent/*）：携带活动中的 Agent，用来观察或拦截飞行中的工作。
  • 能力事件：把策略和适配器挂到接缝上，不用 import loop。

选错域的症状很典型：你写了一个只在当前进程有效的拦截，重启之后行为就变了。那不是 bug，是放错了地方。

至于”要不要改 agent-loop”，我的经验是先默认不改。dsh 的约定是：新行为走已文档化的扩展点；真要改 loop，就得同步更新架构文档——这条约束本身就说明它不是常规操作。

十、四周路线怎么走

手册最后给了一条四周路线，我按它走了一遍，觉得节奏合理：

  • 第 1 周：装配与脊柱。把 profile / bundle / patch 走通，认全六个 ctx key。
  • 第 2 周：turn 生命周期。反复读那一张流程图，直到能凭记忆说出每一步提交了什么。
  • 第 3 周：工具与会话。重点看 pre 与 post，以及 deriveMessages() 的输入。
  • 第 4 周：接缝与宿主。挑一个接缝（比如 ctx.fs），把三个角色都找出来。

每周的验收方式不是”读完”，而是”能指出来”。比如第 2 周的验收是：给我一段日志，我能说出它属于哪一步、为什么在这。

十一、我踩过的四个坑

坑一：以为要改 agent-loop。 实际上九成需求用事件或工具就够了。先翻扩展点，再考虑动主干。

坑二：把会话当成数据库。 它是追加式日志，查询能力来自投影，不是来自索引。想按业务字段查，应该写投影，不是加表。

坑三：想着通读 363 个包。 读完也记不住。正确的做法是顺着主路径读，用到哪个分支再展开哪个分支。

坑四：把 service 当成 seam。 只有一个服务、没有消费者，不叫接缝。写新能力前先想清楚谁会用。

自测清单

读完这份手册，我用下面六个问题自检。能全答上来，基本就能改代码了：

  • profile、bundle、patch 三层的覆盖关系是什么？为什么改配置有时不生效？
  • 六个核心 ctx key 分别负责什么？
  • 一个 turn 里，system prompt 与用户消息在哪一步提交？取消时会发生什么？
  • 工具管线的四个位置分别适合挂什么策略？
  • 为什么说”模型可见就意味着已记录”？这条规则限制了什么写法？
  • 能力接缝的三个角色分别是什么？缺一个会怎样？
