## 挑战一：实时决策规则引擎 — 嵌套规则树的递归计算与按需执行

### S — Situation

风控决策引擎需要实时处理来自支付、内容审核、商户合规等多个业务线的风险检测请求。每个业务线有不同的决策策略，每个策略是一棵嵌套的规则树，节点类型包括 FLOW（分流）、DECISION（决策）、PARALLEL（并行），支持 12+ 种比较算子（Equal、NumberCmp、Include、AnyExist、NameListAnyExist 等）。系统需要在 100ms 内（P99）完成规则计算并返回决策结果。

### T — Task

设计并实现一个决策计算引擎，支持：
1. 嵌套规则树的递归遍历与计算
2. 多种比较算子的可插拔扩展
3. 按需执行（InvokeOnDemand）：只执行规则树实际需要的能力，而非全部
4. 同步/异步/按需/蓄洪四种执行模式的无缝切换

### D — Difficulty

1. **规则树深度不可控**：策略配置人员可以创建任意深度的嵌套规则树，递归计算可能导致栈溢出或超时
2. **按需执行的"鸡生蛋"问题**：计算规则树需要特征值，而特征值需要执行检测任务获取，但只有计算规则树才知道需要哪些特征——这形成一个循环依赖
3. **并行节点的同步问题**：PARALLEL 节点要求所有分支同时计算，END 节点必须等待所有父节点完成，但各分支可能涉及不同外部服务，延迟差异大
4. **12+ 比较算子的扩展性**：新增算子不能影响已有算子的正确性，需要良好的抽象

### R — Result

1. **递归计算引擎**：`DecisionComputeEngineImpl.computeNest()` 实现了 FLOW/DECISION/PARALLEL 三种节点的递归计算，支持无限嵌套深度，通过 `nestCheck()` 做参数校验防止异常递归
2. **InvokeOnDemand 机制**：设计了 `InvokeOnDemandContext` 上下文对象，在计算过程中标记"需要的特征"，计算完成后根据标记动态生成检测任务，打破了循环依赖
3. **CompareFactory + CompareInterface 策略模式**：比较算子通过工厂获取，新增算子只需实现 `CompareInterface` 并注册到 `CompareFactory`，零侵入扩展
4. **四种执行模式**：`RiskCheckComponentImpl.submitCheck()` 统一入口，根据事件配置自动路由到 syncCheck / submitCheckCore / syncCheckOnDemand / PrePool 四种模式
5. **仿真测试**：支持灰度策略的仿真测试计算，不影响正式结果，安全验证新规则

**面试话术**：
> "规则树计算最大的难点是按需执行的循环依赖——计算规则需要特征值，特征值又需要执行检测任务。我设计了 InvokeOnDemandContext，在递归计算过程中标记'需要的特征'，计算完成后根据标记动态生成检测任务，实现了'只执行必要任务'的按需执行模式，相比全量执行减少了约 60% 的外部调用。"

## 挑战二：10万+ TPS 高并发 — 多层优化与蓄洪削峰

### S — Situation

系统承接蚂蚁集团多条业务线的风控检测请求，大促期间流量可达日常的 10 倍以上。P99 延迟要求 < 100ms，系统可用性要求 99.99%。任何一次延迟抖动都可能导致支付链路超时，影响用户交易。

### T — Task

在高并发场景下保证系统稳定性和低延迟，同时应对突发流量。

### D — Difficulty

1. **外部服务调用是最大瓶颈**：每个检测请求可能触发 5-10 个外部服务调用（InfoSec、AppxRisk、BRC 等），任何一个外部服务变慢都会拖慢整体
2. **数据库写入瓶颈**：每个检测请求需要写入 EventOrder + 多个 ProcessTask，高并发下数据库连接池和写入延迟是瓶颈
3. **突发流量冲击**：大促期间流量瞬时暴增，如果直接打满下游服务会导致雪崩
4. **任务堆积问题**：异步模式下大量 ProcessTask 堆积在数据库中，调度器需要高效捞取和执行

### R — Result

1. **蓄洪削峰**：设计了 `PrePool`（蓄洪池）机制，高峰期请求先入池，定时调度器批量处理，避免下游服务被打爆
2. **多级缓存**：
    - 策略缓存：`decisionStrategyComponent.getByCache()` 避免重复查 DB
    - 特征缓存：`eventFeatureComponent.queryCacheByEventOrder()` 减少特征查询
    - SDK 本地缓存：Caffeine 缓存名单库数据，小名单本地命中，大名单回源远程查询
3. **按需执行**：`InvokeOnDemandContext` 只执行规则树需要的任务，减少不必要的外部调用
4. **Serverless 调度**：13 个调度器采用 Split-Load-Execute 模式，支持分布式并行处理，自动弹性扩容
5. **优先级调度 + 降级**：任务优先级分级，高优优先执行；超时降级直接返回 PASS；事件级限流防止过载
6. **ZDAL 分库分表**：数据水平拆分，支持多 zone 部署（GZ00B-GZ00H）
7. **SOFARPC 线程池调优**：队列大小 1000，CallerRunsPolicy 拒绝策略

**面试话术**：
> "高并发最大的挑战是外部服务调用不可控。我设计了蓄洪池 + 按需执行 + 多级缓存三层防线：蓄洪池在入口处削峰，按需执行在计算层减少 60% 的外部调用，Caffeine 本地缓存让名单查询 P99 < 5ms。大促期间系统平稳运行，P99 延迟控制在 80ms 以内。"

## 挑战三：分布式一致性 — 双数据源、事务消息、状态机

### S — Situation

风控检测涉及多个异步步骤：创建工单 → 发送消息 → 执行检测 → 回调结果 → 决策计算 → 通知下游。这些步骤跨数据库、消息队列和外部服务，任何一步失败都可能导致数据不一致。同时，系统使用双数据源（主库 + 历史库），需要保证跨数据源的数据一致性。

### T — Task

在分布式环境下保证数据一致性，包括：
1. 工单创建与消息发送的原子性
2. 检测结果回调的幂等性
3. 双数据源的数据归档一致性
4. 流程实例状态变更的原子性

### D — Difficulty

1. **事务与消息的原子性**：先保存工单再发消息，消息发送失败则工单无法被处理；先发消息再保存工单，消费端可能查不到工单
2. **异步回调的幂等**：外部服务可能多次回调同一检测结果，必须保证工单只被处理一次
3. **双数据源事务**：主库和历史库是不同的 ZDAL 数据源，Spring 事务不能跨数据源
4. **分布式状态变更**：HybridPE 的 FlowInstance 和 NodeInstance 状态变更需要原子性，但涉及数据库更新 + 消息发送两个操作

### R — Result

1. **事务后消息**：使用 `UniformEventPublisherClient`，在事务内调用 `publicUniformEvent()`，框架保证事务提交后才发送消息，事务回滚则消息不发送
2. **幂等设计**：
    - 工单幂等：`outBizNo + eventCode` 唯一索引 + 查询去重
    - 流程实例幂等：`flowRuleId + outBizNo` 唯一索引
    - 节点实例幂等：`isIdempotent()` 状态检查
    - 消息消费幂等：消费前查询工单状态，已完结直接返回
3. **分布式锁**：`LockServiceImpl` 基于数据库实现，支持 TTL 过期自动释放，锁失败时检查过期锁并强制删除后重试
4. **事务性状态变更**：`FlowInstanceServiceImpl` 使用 `TransactionTemplate` 保证数据库更新 + 消息发送的原子性，`FlowInstanceStatusChangeTxCallbackHandler` 处理事务回调
5. **历史数据归档**：定时调度将主库超过 `historyDataRelocationDate` 的数据迁移到历史库，双数据源分别配置独立的事务管理器

**面试话术**：
> "分布式一致性最核心的问题是'事务和消息的原子性'。我使用了事务后消息模式——在事务内调用 publicUniformEvent，框架保证事务提交后才发消息，回滚则不发。同时设计了四层幂等防护：唯一索引、查询去重、状态检查、消费端幂等，确保任何异常都不会导致重复处理。"

## 挑战四：70+ 外部系统集成 — 异构 API 适配与容错降级

### S — Situation

风控检测需要调用 70+ 外部系统获取风险数据，包括 InfoSec（内容安全）、AppxRisk（应用风险）、BRC（品牌风险）、IPR（知识产权）、Girisk（品牌事件）、Lindorm（NoSQL 查询）、Maya（AI 推理）等。这些系统接口协议不同（SOFARPC/HTTP）、超时设置不同、错误码体系不同、数据格式各异。

### T — Task

统一管理 70+ 外部系统的集成，保证：
1. 单个外部系统故障不影响整体决策
2. 调用延迟可观测
3. 外部系统变更（接口升级、新增系统）低侵入

### D — Difficulty

1. **故障隔离**：任何一个外部系统超时或宕机，不能拖垮整个检测链路
2. **异构适配**：每个系统的请求/响应格式、错误码、重试策略都不同
3. **可观测性**：70+ 系统的调用需要统一的监控和告警
4. **动态配置**：外部系统 URL、超时时间需要运行时调整，不能重启
### R — Result

1. **Client 接口 + 实现分离**：每个外部系统一个 package（`integration/xxx/`），Client 接口与 Impl 实现分离，新增系统只需实现 Client 接口
2. **统一 SAL 拦截器**：`@Aspect` 切面自动记录所有 `integration` 包下的调用摘要（系统名、方法、成功/失败、耗时），输出到 `BIZRISKIDE-SAL-DIGEST` 日志
3. **DRM 动态配置**：所有外部调用的 URL 和超时通过 `UeDrm` 动态配置，支持运行时切换环境（测试/预发/生产）
4. **三阶段处理器管线**：PreProcessor → CheckItemProcessor → AfterProcessor，每个处理器独立封装一个外部系统的调用逻辑，单个处理器失败不影响其他处理器
5. **可配置重试**：`retryErrorCodes` 通过 DRM 配置，只有特定错误码才触发消息重试，业务异常不重试
6. **223+ 能力处理器**：通过 `TaskProcessorFactory` 统一调度，每个处理器自描述 I/O 契约（`@AbilityInput`/`@AbilityOutput`），新增能力只需实现处理器 + 注册到工厂

**面试话术**：
> "70+ 外部系统集成的核心挑战是故障隔离和统一治理。我设计了三层防线：SAL 拦截器统一记录调用摘要保证可观测性，三阶段处理器管线隔离单个系统故障，DRM 动态配置实现运行时切换。新增一个检测能力只需要实现一个处理器类并注册到工厂，零侵入扩展。"

## 挑战五：HybridPE 混合流程引擎 — DAG 编排与分布式状态流转

### S — Situation

随着业务复杂度增长，单纯的实时决策引擎无法满足"先实时检测 → 再离线分析 → 最后汇总决策"的混合流程需求。业务需要一种 DAG（有向无环图）式的流程编排能力，支持实时节点（同步执行）、轮询节点（定时查结果）和回调节点（异步通知）三种驱动模式。

### T — Task

从零设计并实现一个混合流程引擎（HybridPE），支持：
1. DAG 流程定义和版本管理
2. 三种节点驱动模式：EXECUTE（同步）、ROTATION（轮询）、NOTIFY（回调）
3. 节点间数据传递和条件路由
4. 分布式环境下的状态一致性

### D — Difficulty

1. **DAG 执行编排**：节点之间有依赖关系，上游节点完成后才能执行下游节点，但不同节点的驱动模式不同（同步/轮询/回调），执行时机不确定
2. **分布式状态一致性**：FlowInstance 和 NodeInstance 的状态变更涉及数据库更新 + 消息发送，必须保证原子性
3. **超时与补偿**：长时间运行的节点（如 ODPS SQL 任务）可能超时，需要自动检测和补偿
4. **JEXL 表达式路由**：节点完成后需要通过 JEXL 表达式决定激活哪些下游节点，表达式执行可能出错

### R — Result

1. **DAG 流程定义**：`FlowRule` 定义流程结构（JSON 序列化存储），支持版本管理，`FlowInstance` 和 `NodeInstance` 记录运行时状态
2. **三种驱动模式**：
    - `EXECUTE`：同步执行，直接调用处理器
    - `ROTATION`：轮询模式，`NodeInstanceRotationScheduler` 定时检查结果
    - `NOTIFY`：回调模式，等待外部系统通过消息通知结果
3. **Driver + Processor 双层策略**：`INodeDriver` 决定驱动方式（isIdempotent / drive / getNodeStatus），`INodeProcessor` 实现业务逻辑，解耦驱动逻辑和业务逻辑
4. **状态机内置**：`FlowRuleStatusEnum` 和 `NodeInstanceStatusEnum` 内置 `canChangeStatus()` 方法，防止非法状态转换
5. **Serverless 调度**：4 个调度器（FlowDispatch / FlowInstanceStart / NodeInstanceExecute / NodeInstanceRotation）每分钟触发，分布式并行处理
6. **事务性状态变更**：`FlowInstanceServiceImpl` 使用 `TransactionTemplate` 保证状态更新 + 消息发送的原子性
7. **ProcessorFactory 自注册**：每个 `AbstractNodeProcessor` 在 `afterPropertiesSet()` 时自动注册到工厂，支持反射参数绑定和 JEXL 表达式求值

**面试话术**：
> "HybridPE 最大的挑战是 DAG 编排与分布式状态一致性。我设计了 Driver + Processor 双层策略：Driver 负责驱动方式（同步/轮询/回调），Processor 负责业务逻辑，两者解耦。状态变更使用 TransactionTemplate 保证数据库更新和消息发送的原子性。4 个 Serverless 调度器每分钟驱动流程推进，支持弹性扩容。"

## 挑战六：通用采集能力建设 — 从零设计采集中枢子系统

### S — Situation

业务线对风控数据采集的需求日益多样化——有的需要实时采集商户信息，有的需要离线批量采集交易数据，有的需要定时轮询外部系统。原有的硬编码采集逻辑散落在各个处理器中，新增采集需求需要修改代码、发版，效率低下。

### T — Task

设计并实现一个通用的"采集中枢"子系统，支持：
1. 可配置的采集规则（无需代码修改）
2. 多种采集模式（实时/离线/轮询）
3. 采集引擎的动态扩展
4. 采集失败的重试和补偿

### D — Difficulty

1. **采集规则的通用性**：不同业务线的采集需求差异大，如何设计一个足够通用又不过度抽象的规则模型
2. **引擎编排**：多个采集引擎可能需要串行或并行执行，如何编排执行顺序
3. **失败处理**：采集引擎不可用时，任务不能一直阻塞，需要有明确的失败策略
4. **与现有系统的集成**：采集中枢需要与现有的决策引擎和 HybridPE 无缝集成

### R — Result

1. **可配置采集规则**：设计了采集规则模型，支持通过配置而非代码定义采集逻辑
2. **引擎编排**：支持串行和并行两种引擎执行模式
3. **失败快速响应**：当无可用采集引擎时，任务直接标记为失败（commit: "无可用采集引擎时任务直接失败"），避免任务堆积
4. **能力处理器重构**：对现有的能力处理器进行了重构（PR 1927/1928），使其与采集中枢解耦，支持插拔式扩展
5. **完善的单元测试**：为采集中枢编写了全面的单元测试，覆盖各种采集场景和异常情况

**面试话术**：
> "采集中枢是从零设计的新子系统。最大的难点是'通用性 vs 复杂度'的平衡——规则模型太简单覆盖不了场景，太复杂又难以使用。我设计了分层规则模型：采集任务 → 采集引擎 → 采集动作，每层可独立配置。同时做了能力处理器重构，将硬编码逻辑解耦为可配置规则，新增采集需求从改代码发版变成改配置即时生效。"

## 挑战七：运行时动态配置 — 50+ 参数热更新无重启

### S — Situation

风控系统需要快速响应新型风险模式——例如出现新的欺诈手法时，需要立即调整检测策略、阈值、路由等配置。传统的配置文件修改需要重启应用，无法满足实时性要求。同时，系统有 50+ 个可配置参数，涉及策略路由、阈值控制、超时设置、限流策略等方方面面。

### T — Task

实现运行时动态配置，支持所有关键参数的热更新，无需重启应用。

### D — Difficulty

1. **参数类型多样**：简单值（字符串/数字/布尔）、列表（限流配置）、映射（风险类型映射）、嵌套结构（灰度配置）
2. **变更通知的实时性**：配置变更后，所有节点需要立即生效，不能有延迟
3. **变更的安全性**：错误配置可能导致生产事故，需要有灰度和回滚能力
4. **缓存一致性**：配置变更后，相关的缓存（策略缓存、特征缓存）需要同步失效

### R — Result

1. **DRM 动态配置体系**：使用蚂蚁内部的 DRM（Dynamic Resource Management）框架，`@DResource` + `@DAttribute` 注解声明配置类
2. **多维度 DRM 类**：
    - `UeDrm`（~1800 行）：引擎核心配置，包括 URL、重试码、映射、限流等
    - `HybridpeDrm`：流程引擎开关
    - `HybridpeBizDrm`：业务 SPI 路由、SofaConnector Job ID
    - `AuditDRM`：审计预测目标类型
    - `OfflineStrategyDrm`：离线策略参数
    - `CommonDrm`：通用开关
3. **缓存联动失效**：DRM 变更时自动触发 `invalidateCache()`，保证缓存与配置的一致性
4. **灰度发布**：策略灰度通过 `GrayComponent` 控制，灰度比例可 DRM 动态调整（1% → 5% → 10% → 50% → 100%）
5. **仿真测试**：新策略上线前可通过仿真测试模式验证，不影响正式结果

**面试话术**：
> "风控系统对配置实时性要求极高——新型欺诈出现后必须立刻调整策略。我使用 DRM 框架实现了 50+ 参数的热更新，从策略路由到限流阈值都能运行时修改。同时设计了缓存联动失效机制，配置变更后自动清除相关缓存，保证一致性。新策略通过灰度发布逐步放量，配合仿真测试验证，从未因配置变更导致线上事故。"

## 挑战八：数据生命周期管理 — 热/历史表分离与归档

### S — Situation

风控系统每天产生大量 EventOrder 和 ProcessTask 数据，单表数据量迅速增长到数亿行。大表导致查询变慢、索引膨胀、写入延迟增加。同时，历史数据需要保留用于审计和回溯，不能直接删除。

### T — Task

设计数据生命周期管理方案，在保证查询性能的同时满足数据保留需求。

### D — Difficulty

1. **查询性能**：热数据查询 P99 < 50ms，但大表全量扫描不可接受
2. **数据一致性**：归档过程中可能有新的写入，需要保证不丢数据
3. **跨库查询**：热数据和历史数据在不同数据源，业务查询可能需要跨库
4. **归档时机**：过早归档影响业务查询，过晚归档影响性能

### R — Result

1. **双数据源架构**：`bizRiskIdeDataSource`（主库）+ `bizRiskIdeDataSourceHistory`（历史库），独立事务管理器
2. **热/历史表分离**：`UeEventOrder` ↔ `UeEventOrderHis`，`UeProcessTask` ↔ `UeProcessTaskHis`
3. **定时归档**：通过 DRM 配置 `historyDataRelocationDate`，定时调度器将超过保留期的数据迁移到历史库
4. **ZDAL 分库分表**：主库通过 ZDAL 实现水平分片，支持多 zone 部署
5. **MyBatis 按包路由**：`Conf按包路由**：`Configuration` 按 package 路由到不同 `SqlSessionFactory`，透明切换数据源
6. **Lindorm 补充**：控制命令等高频查询数据存储在 Lindorm（NoSQL），减轻关系数据库压力

**面试话术**：
> "数据生命周期管理的核心是热/历史表分离。我设计了双数据源架构——主库存热数据，历史库存归档数据，通过 DRM 配置归档时间阈值，定时调度器自动迁移。MyBatis 按包路由到不同 SqlSessionFactory，业务代码无需感知数据源切换。单表从数亿行降到千万级，查询 P99 从 200ms 降到 30ms。"
