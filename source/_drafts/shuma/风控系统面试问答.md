## 一、架构设计类

### Q1: 你们系统如何支撑10w TPS的高并发？从架构层面说说你的理解。

**答案要点**：

从五个层面来支撑高并发：

**1. 微服务架构 + 水平扩展**
```
┌─────────────────────────────────────────────────────────────┐
│                    SOFABoot 3.20.0                          │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐   │
│  │ 实时引擎 │  │ 离线引擎 │  │ 混合引擎 │  │ 调度器   │   │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘   │
└─────────────────────────────────────────────────────────────┘
         │              │              │              │
    ┌────┴────┐    ┌────┴────┐    ┌────┴────┐    ┌────┴────┐
    │ ZDAL    │    │ SOFAMQ  │    │  DDS    │    │ Redis   │
    │ 分库分表 │    │ 消息队列 │    │ 配置中心 │    │ 缓存    │
    └─────────┘    └─────────┘    └─────────┘    └─────────┘
```
- 通过ZDAL实现分库分表，数据水平扩展
- RPC线程池队列配置：`thread.pool.queue.size=1000`

**2. 四种执行模式灵活切换**
- **同步检测**：简单规则，立即返回，适合低延迟场景
- **异步检测**：复杂规则，返回CC后后台执行，适合高吞吐场景
- **按需执行**：动态生成任务，只执行必要的检测
- **蓄洪模式**：高峰期先入池，定时批量处理，削峰填谷

**3. Serverless调度架构**
- 任务按需触发，自动弹性伸缩
- Splitor分片 → Loader加载 → Executor执行，分布式并行

**4. 缓存策略**
- 策略缓存：`decisionStrategyComponent.getByCache()`
- 特征缓存：`eventFeatureComponent.queryCacheByEventOrder()`

**5. 并行计算**
- PARALLEL节点类型支持多分支同时计算
- 检测任务并行执行

### Q2: 你们系统有同步和异步两种检测模式，什么场景用哪种？为什么这样设计？

**答案要点**：

| 模式 | 适用场景 | 延迟要求 | 规则复杂度 | 吞吐量 |
|-----|---------|---------|-----------|-------|
| **同步检测** | 支付前风控、登录验证 | < 100ms | 简单规则 | 中等 |
| **异步检测** | 内容审核、批量数据检测 | 秒级~分钟级 | 复杂规则 | 高 |
| **按需执行** | 动态规则、中等复杂度 | < 500ms | 中等 | 中高 |
| **蓄洪模式** | 大促期间、流量高峰 | 分钟级 | 任意 | 极高 |

**设计原因**：

1. **同步检测**：
    - 用户等待场景，必须快速返回
    - 规则简单，特征已准备好
    - 代码路径：`syncCheck()` 同步执行所有任务

2. **异步检测**：
    - 用户无需等待，后台慢慢处理
    - 规则复杂，需要调用多个外部能力
    - 返回CC（Continue Check），通过消息回调通知结果

3. **按需执行**：
    - 结合同步和异步的优点
    - 根据规则树动态决定执行哪些任务
    - 通过`InvokeOnDemandContext`控制

4. **蓄洪模式**：
    - 应对突发流量
    - 先存入`PrePool`，定时调度批量处理
    - 避免系统过载

**代码判断逻辑**：
```java
// 判断是否同步事件
private Boolean isSync(Event event) {
    String processModel = (String) MapUtil.safeGet(event.getConfigParams(), EventConfigParamEnum.PROCESS_MODEL.getCode());
    return StringUtil.equals(processModel, "sync");
}

// 判断是否按需执行
private boolean isSyncOnDemand(DecisionStrategy decisionStrategy) {
    DecisionStrategyRuleNode ruleNode = decisionStrategyRuleComponent.getByCache(...);
    return ruleNode.isInvokeSync() && ruleNode.isInvokeOnDemand();
}
```

### Q3: 你们的决策规则树是怎么设计的？支持哪些类型的节点？

**答案要点**：

**规则树结构**：
```
                    ┌──────────────────┐
                    │   START节点      │
                    └────────┬─────────┘
                             │
                             ▼
                    ┌──────────────────┐
                    │   FLOW节点       │
                    │  (分流/路由节点)  │
                    └────────┬─────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
              ▼              ▼              ▼
       ┌──────────┐   ┌──────────┐   ┌──────────┐
       │DECISION  │   │DECISION  │   │DECISION  │
       │(决策节点) │   │(决策节点) │   │(决策节点) │
       └──────────┘   └──────────┘   └──────────┘
```

**三种节点类型**：

| 节点类型 | 功能 | 执行逻辑 |
|---------|------|---------|
| **FLOW** | 流量分流 | 根据条件表达式走向不同分支 |
| **DECISION** | 决策计算 | 计算所有表达式，汇总命中结果 |
| **PARALLEL** | 并行执行 | 同时计算多个分支，END节点等待所有完成 |

**核心实现**：
```java
private void computeNest(DecisionStrategyRuleNode ruleNode, ...) {
    // 计算条件表达式
    Map<String, BooleanExt<String>> expressionResultMap = computeExpressions(...);

    if (RuleNodeTypeEnum.FLOW.equals(ruleNode.getRuleNodeType())) {
        // 分流节点：命中哪个关系表达式，走向哪个分支
        for (DecisionExpressionRelation relation : ruleNode.getExpressionRelationList()) {
            Boolean result = ExpressionRelationUtil.compute(relation.getRelationStr(), expressionHitResultMap);
            if (result) {
                DecisionStrategyRuleNode nextRuleNode = getFlowNodeHitRelationRuleNode(relation, ...);
                computeNest(nextRuleNode, ...); // 递归计算
         }
        }
    } else if (RuleNodeTypeEnum.DECISION.equals(ruleNode.getRuleNodeType())) {
        // 决策节点：汇总所有命中的结果
        for (DecisionExpressionRelation relation : ruleNode.getExpressionRelationList()) {
            Boolean result = ExpressionRelationUtil.compute(...);
            if (result) {
                ruleNodeComputeResult.getHitExpressionRelations().add(relation);
            }
        }
    } else if (RuleNodeTypeEnum.PARALLEL.equals(ruleNode.getRuleNodeType())) {
        // 并行节点：同时计算所有子节点
        for (DecisionStrategyRuleNode childNode : ruleNode.getNextNodes()) {
            computeNest(childNode, ...);
        }
    }
}
```



**表达式支持**：
- 操作符：`>`, `<`, `==`, `!=`, `>=`, `<=`, `contains`, `in`, `not_in`
- 逻辑运算：`&&`, `||`, `!`
- 示例：`age > 18 && risk_score >= 80`

### Q4: 你们系统如何保证消息不丢失？事务和消息如何保证一致性？

**答案要点**：

**问题背景**：
- 异步检测模式下，需要先保存工单，再发送消息触发后续处理
- 如果先发消息再保存工单，消息消费时可能工单还没保存成功
- 如果先保存工单再发消息，消息发送失败会导致工单无法被处理

**解决方案：事务后消息**

```java
// 使用 UniformEventPublisherClient 保证事务后发送
@Autowired
private UniformEventPublisherClient uniformEventPublisherClient;

// 在事务内调用，框架保证事务提交后再发送消息
bizRiskIdeTransactionTemplate.execute(new TransactionCallback<CheckResult>() {
    @Override
    public CheckResult doInTransaction(TransactionStatus status) {
        // 1. 保存工单
        saveEventOrder(eventOrder);
        // 2. 保存任务
        processTaskComponent.batchCreate(processTaskList);
        // 3. 返回结果（消息在事务提交后自动发送）
        return contructCCResult(eventOrder, event);
    }
});
```

**UniformEventPublisherClient原理**：
1. 在事务内调用`publicUniformEvent()`
2. 框架将消息暂存到本地内存表
3. 事务提交成功后，框架自动发送消息
4. 如果事务回滚，消息不会发送

**消息消费幂等性**：
```java
// 通过 outBizNo + eventCode 唯一索引保证幂等
EventOrder existEventOrder = eventOrderComponent.queryByOutBizNo(request.getOutBizNo(), request.getEventCode());
if (existEventOrder != null) {
    return convertCheckResult(existEventOrder, request.getEventCode());
}
```

### Q5: 你们系统如何处理分布式锁？有什么需要注意的地方？

**答案要点**：

**使用场景**：
1. 流程实例状态变更
2. 节点实例执行
3. 任务优先级更新

**实现方式**：
```java
// FlowExecutorImpl.java - 流程实例加锁
String lockId = null;
try {
    // 1. 加锁
    lockId = lockService.lock(instanceId, LockTypeEnum.FLOW_INSTANCE, 10);
    
    // 2. 执行业务逻辑
    FlowInstanceModel flowInstanceModel = flowInstanceService.getFlowInstanceById(instanceId);
    // ... 状态检查和更新
    
} finally {
    // 3. 释放锁
    lockService.unlock(lockId);
}
```

**注意事项**：

1. **锁超时设置**：
    - 设置合理的锁超时时间（如10秒）
    - 避免业务执行时间超过锁超时时间

2. **锁粒度选择**：
    - 流程实例级别锁：`LockTypeEnum.FLOW_INSTANCE`
    - 节点实例级别锁：`LockTypeEnum.NODE_INSTANCE`
    - 粒度越细，并发度越高，但管理越复杂

3. **死锁预防**：
    - 使用`try-finally`保证锁释放
    - 避免嵌套加锁
    - 按固定顺序加锁

4. **幂等设计**：
   ```java
   // 加锁后再次检查状态，避免重复执行
   if (FlowInstanceStatusEnum.PROCESSING.equals(flowInstanceModel.getStatus())
       || FlowInstanceStatusEnum.FINISHED.equals(flowInstanceModel.getStatus())) {
       return true; // 幂等返回
   }
   ```

### Q6: Serverless调度是怎么实现的？和传统调度有什么区别？

**答案要点**：

**传统调度 vs Serverless调度**：

| 特性 | 传统调度 (Quartz/Crontab) | Serverless调度 |
|-----|-------------------------|----------------|
| **资源占用** | 常驻进程，持续占用资源 | 按需启动，用完释放 |
| **扩容方式** | 手动扩容机器 | 自动弹性伸缩 |
| **执行模式** | 单机执行 | 分布式并行执行 |
| **任务分片** | 需要自己实现 | 框架内置Splitor |
| **配置管理** | 本地配置文件 | DDS动态配置中心 |
| **容错能力** | 单点故障风险 | 自动重试+故障转移 |

**四组件模式**：
```
┌─────────────────────────────────────────────────────────────────┐
│   ┌──────────────┐                                              │
│   │   Runtime    │  ← 调度入口，定义cron表达式和执行流程          │
│   │  Scheduler   │                                              │
│   └──────┬───────┘                                              │
│          │                                                       │
│          ▼                                                       │
│   ┌──────────────┐                                              │
│   │   Splitor    │  ← 任务分片，决定拆分成多少个子任务            │
│   └──────┬───────┘                                              │
│          │                                                       │
│          ▼                                                       │
│   ┌──────────────┐                                              │
│   │    Loader    │  ← 数据加载，从数据库捞取待处理的任务数据      │
│   └──────┬───────┘                                              │
│          │                                                       │
│          ▼                                                       │
│   ┌──────────────┐                                              │
│   │   Executer   │  ← 任务执行，执行具体的业务逻辑               │
│   └──────────────┘                                              │
└─────────────────────────────────────────────────────────────────┘
```

**代码实现**：
```java
@Scheduler(name = "EC_BIZRISKIDE_FLOW_INSTANCE_START")
@SchedulerTaskSpec(cron = "0 */1 * * * ?")  // 每分钟触发
@Component
public class FlowInstanceStartScheduler {

    @Ingress
    @Func(next = "load")
    public List<DataLoadFilterItem> split(ServerlessClusterJobExecuteContext<?> context) {
        return splitor.split();  // 分片
    }

    @Func(next = "execute")
    public List<String> load(ServerlessClusterJobExecuteContext<FlowInstanceStartFilterItem> context) {
        return loader.load(context.getChunk());  // 加载数据
    }

    @Func
    public ServerlessCommonResult execute(ServerlessClusterJobExecuteContext<String> context) {
        executer.execute(context.getChunk());  // 执行任务
        return ServerlessCommonResult.buildSuccessResult();
    }
}
```

**执行流程**：
1. 每分钟触发调度
2. Splitor读取配置，决定每次加载多少条数据
3. Loader从数据库查询待处理的工单
4. Executor分布式并行执行每个工单

### Q8: 如果检测任务执行失败怎么办？你们有重试机制吗？

**答案要点**：

**重试机制设计**：

```java
// 1. 执行次数校验
private Boolean isPassCheckByMaxTimes(ProcessTask processTask) {
    int executeTimes = getExecuteTimes(processTask);
    
    // 最多重试10次
    if (executeTimes >= 0 && executeTimes <= MAX_EXE_TIMES) {
        return true;
    }
    return false;
}

// 2. 记录执行次数
private Integer saveExeTimes(String processTaskId) {
    LockResult<ProcessTask> lockResult = processTaskComponent.lockById(processTaskId);
    int exeTimes = Integer.parseInt(extInfo.get("EXE_TIMES").toString());
    exeTimes++;
    extInfo.put("EXE_TIMES", String.valueOf(exeTimes));
    processTaskComponent.updateById(processTask);
    return exeTimes;
}

// 3. 优先级降级
// 每执行10/20/40/80/160/320...次降低一个最高位优先级
if (executeTimes >= 10 && executeTimes % 10 == 0 && isPowerOfTwo(executeTimes / 10)) {
    modifyTaskPriority(processTaskId, declinePriorityByOne(priority));
}
```

**失败处理流程**：
1. 任务执行失败，状态变为`FAIL`
2. 调度器重新拉取`INIT`状态的任务重试
3. 重试次数达到上限，任务最终失败
4. 触发告警，人工介入

**补偿机制**：
```java
// 后置处理失败时发送补偿消息
private void sendAfterTaskErrorCompensateMessage(String processTaskId) {
    ControlCommandRequest request = buildControlCommandRequest(processTaskId);
    uniformEventPublisherClient.publicUniformEvent(TOPIC, AFTER_COMPENSATE_EVENT_CODE, request);
}
```

## 四、业务理解类

### Q9: 你们的风控决策流程是怎样的？从用户发起请求到返回结果，完整说一下。

**答案要点**：

**完整流程**：

```
1. 用户发起支付请求
       │
       ▼
2. 业务系统调用 DecisionFacade.submitDecision()
       │
       ▼
3. DecisionComponent 查询事件配置，判断执行模式
       │
       ├─? 同步模式：直接执行，返回结果
       │
       └─? 异步模式：创建工单和任务，返回CC
              │
              ▼
4. RiskCheckComponent 创建 EventOrder + ProcessTask
       │
       ▼
5. TaskProcessorEngine 执行任务
       │
       ├─? PreProcessor：数据准备、特征提取
       │
       └─? CheckItemProcessor：风险检测
              │
              ▼
6. DecisionComputeEngine 决策计算
       │
       ├─? 获取规则树
       ├─? 构建特征池
       ├─? 递归计算节点
       └─? 汇总结果
              │
              ▼
7. 返回决策结果
       │
       ├─? PASS：通过
       ├─? REJECT：拒绝
       ├─? CC：继续检测
       └─? CLOSE：关闭
              │
              ▼
8. 业务系统根据结果处理

       ├─? PASS：允许支付
       └─? REJECT：拦截支付
```

**关键数据流**：
- **请求参数**：`outBizNo`(业务单号)、`eventCode`(事件码)、`featureItemParams`(特征值)
- **工单**：记录一次风控检测的全过程
- **任务**：记录每个检测步骤的执行状态
- **决策结果**：`resultCode` + `hitValueList`(命中的风险类型)

### Q12: 你们的状态机是怎么设计的？为什么要这样设计？

**答案要点**：

**双状态机设计**：

**1. EventOrder（工单）状态机**
```
PRE_PENDING ──? AUTO_PENDING ──? PASS/REJECT/CLOSE
      │              │
      │              └──? MANUAL_PENDING ──? PASS/REJECT
      │
      └──? CANCEL
```

**状态说明**：
- `PRE_PENDING`：待前置处理，等待数据准备
- `AUTO_PENDING`：自动处理中，正在执行检测
- `MANUAL_PENDING`：人工待审，需要人工介入
- `PASS`：通过
- `REJECT`：拒绝
- `CLOSE`：关闭
- `CANCEL`：取消

**2. ProcessTask（任务）状态机**
```
INIT ──? READY ──? PENDING ──? END
  │                             │
  │                             └──? FAIL ──? INIT (重试)
  │
  └──? LAZY_INIT ──? INIT
  │
  └──? WAIT ──? INIT
```

**状态说明**：
- `INIT`：初始化，刚创建
- `READY`：就绪，可以执行
- `PENDING`：执行中，等待结果
- `END`：完成
- `FAIL`：失败
- `LAZY_INIT`：延迟初始化，限流场景
- `WAIT`：等待依赖任务完成

**设计原因**：

1. **精确控制执行流程**：
    - 不同状态对应不同的处理逻辑
    - 避免重复执行或遗漏执行

2. **支持断点续传**：
    - 任务失败后可以从当前状态继续
    - 不需要从头开始

3. **便于监控和排查**：
    - 清晰的状态流转日志
    - 快速定位问题所在阶段

4. **支持人工介入**：
    - `MANUAL_PENDING`状态支持人工审核
    - 审核完成后继续自动流程

**状态变更代码**：
