一个商品详情页每秒收到几千次请求，但商品名称和图片一天只改几次。如果每次请求都查数据库，大部分查询是在重复做同一件事。缓存把近期用过的数据放在读取更快的位置，让重复请求少走一段路。

这篇文章先回答**为什么缓存、缓存在哪里**，再认识 Java 常见的缓存方案，最后用一个两级缓存案例说明：数据更新后，为什么用户仍可能读到旧值，以及该怎么处理。

## 一、为什么需要缓存

假设一次数据库查询需要 20 ms，而一次本地内存读取只需很短的时间。把热点商品放进缓存后，大量重复读取可以直接返回，数据库也能腾出连接和算力处理真正需要查询的请求。具体收益要用自己的数据和压测验证，不能把某个延迟数字当成所有系统的承诺。

| 原来的问题 | 例子 | 缓存的作用 |
| --- | --- | --- |
| 重复计算 | 同一段脚本反复编译 | 复用编译结果 |
| 重复读取 | 热门商品每次都查数据库 | 减少查询量和响应时间 |
| 外部调用成本高 | 反复请求远程配置 | 降低网络延迟与调用次数 |

代价同样明确：**缓存里可能是旧数据**，还会占内存、增加失效和排障工作。余额、库存扣减这类正确性要求高的操作，不能因为有缓存就跳过数据库中的并发控制。先判断数据是否“读多写少、允许短时间陈旧、加载成本较高”，再考虑缓存。

### 一次读取是怎样命中的

最常见的做法叫 *Cache Aside*（旁路缓存）：业务代码先读缓存；没找到就查数据库，并把结果放进缓存。写入时通常先更新数据库，再删除相关缓存项；下次读取重新加载。下面的图展示一个项目里不同用途的缓存，后文再拆解其中的两级模型。

![原始项目中的缓存体系总览，区分业务缓存、实例缓存与注解缓存](https://pfa-oss-example.oss-cn-hangzhou.aliyuncs.com/blog/cache-design-overview-20261019.jpeg)

命中率高不等于设计正确。数据库更新后若旧值仍留在缓存里，用户读到的依然是错的。

## 二、缓存可以放在哪里

先看位置，再挑框架。位置决定了速度、共享范围和一致性成本。

| 位置 | 常见实现 | 优点 | 要注意 |
| --- | --- | --- | --- |
| JVM 本地内存 | Caffeine、Guava、Ehcache | 读取快，不经过网络 | 每个应用实例各有一份，重启后消失 |
| 独立缓存服务 | Redis | 多个应用实例可共享 | 有网络开销，要管理服务可用性和内存 |
| 两级缓存 | 本地 Caffeine + Redis | 热点读本地，其余读共享缓存 | 两层都要处理更新和失效 |

**单机、数据量有界、允许各节点短暂不一致**，先考虑本地缓存；**多实例需要共享缓存值**，考虑 Redis；只有性能数据证明单层缓存不够用，才引入两级缓存。数据库始终是本例中的权威数据源。

## 三、Java 生态中有哪些选择

这些名字经常一起出现，但不在同一层：Caffeine、Guava、Ehcache 是本地缓存实现；Redis 是独立缓存服务；Spring Cache 是调用缓存的**抽象接口和注解机制**，并不自行决定数据存在哪里。

| 方案 | 适合什么 | 选用时最重要的判断 |
| --- | --- | --- |
| **Caffeine** | 新项目中的 JVM 本地热点数据 | 支持容量限制、过期、加载和统计；通常是本地缓存的优先选择 |
| **Guava Cache** | 已经使用 Guava 缓存的项目 | 能完成基础加载与过期；新代码可比较 Caffeine |
| **Ehcache** | 需要堆内、堆外或磁盘等存储层的项目 | 按实际存储需求选，配置与运维也更复杂 |
| **Redis** | 多实例共享的缓存 | 有网络和服务故障成本；它不在 Java 进程内 |
| **Spring Cache** | 用 `@Cacheable` 管理方法结果 | 还须配置 Caffeine、Redis 等具体 `CacheManager` |
| **JCache（JSR 107）** | 需要标准化缓存 API | 是规范，不是具体缓存产品 |

### 先从 Caffeine 的一条缓存开始

例如商品详情允许短时间陈旧，可以限制条目数和写入后过期时间：

```java
Cache<Long, Product> products = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(5))
    .build();

Product product = products.get(productId, id -> productRepository.findById(id));
```

这里的 5 分钟只是例子，不是所有商品的推荐 TTL。Caffeine 的 `get` 对同一个 key 的加载有原子计算语义，但数据库失败如何处理、查不到商品时是否缓存空值，仍要由业务定义。`maximumSize` 限制条目数量，不是 JVM 内存字节数；大对象要估算堆占用。

### Spring Cache 解决的是接入方式

在 Spring 项目中，也可以把缓存声明放到查询方法上：

```java
@Cacheable(cacheNames = "products", key = "#id")
public Product findProduct(Long id) {
    return productRepository.findById(id);
}

@CacheEvict(cacheNames = "products", key = "#id")
public void updateProduct(Long id, ProductUpdate command) {
    productRepository.update(id, command);
}
```

这段代码还需要配置具体的缓存实现。`@Cacheable` 依赖 Spring 代理，同一个对象内部直接调用自身方法通常不会经过代理；写入失败、事务回滚与缓存删除的先后顺序也必须检查。注解不会自动替你决定 TTL、key 和一致性策略。

### 什么时候需要 Redis

假设服务部署了三台机器，机器 A 修改了商品，机器 B 的本地缓存不会因为 A 的删除操作自动更新。若业务要求各节点读取同一份缓存，Redis 是直接的选择。它也会遇到穿透、热点 key、服务故障等问题，因此仍要保留数据库回源路径、合理的过期时间和监控。

不要仅仅因为“系统是分布式的”就叠加 Caffeine + Redis。先确认 Redis 是否已满足延迟和吞吐目标；多一层本地缓存，就多一层需要同步失效的旧数据。

## 四、从选框架走到设计缓存

选好了产品，还要回答四个问题：**缓存什么、key 是什么、什么时候过期、数据变化时谁负责删除**。

1. **缓存对象。**优先选热点、加载成本高、读多写少的数据。模型实例、编译结果和商品详情的生命周期不同，不应共用一套 TTL。
2. **设计 key。**key 必须覆盖所有影响结果的条件，例如商品 ID、租户 ID 和语言。漏掉租户 ID，可能把 A 租户的数据给 B 租户。
3. **限制容量和过期。**本地缓存至少考虑容量上限；`expireAfterWrite` 从写入后计时，`expireAfterAccess` 从最近访问后计时。TTL 表示愿意接受的陈旧窗口，不代表到期前一定正确。
4. **处理变更。**数据库写成功后，失效相关 key；一条数据有多个查询入口时，要逐个处理。跨节点本地缓存还需要消息通知、版本化 key，或者接受 TTL 定义的陈旧窗口。

还有三个常见故障：不存在的 key 每次都打到数据库，是**穿透**；热点 key 同时过期，大量请求一起回源，是**击穿**；大量 key 同时过期，造成集中回源，是**雪崩**。按场景分别考虑短时空值、单 key 合并加载、过期时间错峰和限流。数据库故障不能被长期缓存成“数据不存在”。

观察结果：更新数据库之后，L1 还能返回旧实例；只删除 L1，L2 又可能把旧配置装回 L1；删除两级缓存后，下一次读取才会访问数据库。即使 L2 到期，只要 L1 仍命中，请求也不会走到 L2。这解释了为什么“配置缓存 10 分钟过期”不等于“所有用户最多读旧 10 分钟”。

原项目里还有按 `agentCode_version`、`agentId`、`agentCode_status` 三种 key 缓存同一份 Agent 元数据的例子。它们的 TTL 分别是 5、5、1 分钟。修改一条元数据时，三个查询入口都要失效；否则不同页面可能看到不同版本。项目中的提示词模板、Groovy 编译结果和 Spring Cache 方法结果，也分别采用了不同容量与过期策略。

## 六、最后怎么选

第一次给 Java 服务加缓存，可以按这个顺序做：

1. 先量出慢在哪里，确认是重复读取或重复计算，明确可接受的陈旧时间。
2. 单实例或节点间允许短暂差异时，先评估 Caffeine；需要共享时，评估 Redis。Spring Cache 可用于接入已有实现。
3. 为每类数据确定 key、容量、TTL、更新后的失效动作和数据库故障时的行为。
4. 用“更新数据库后立即读取”的测试验证旧值窗口；上线后同时看命中率、回源量、加载耗时、内存占用和错误率。

**缓存是用空间和一致性成本换读取速度。选型只是第一步，真正决定方案是否可靠的是 key、过期、失效与监控。**
