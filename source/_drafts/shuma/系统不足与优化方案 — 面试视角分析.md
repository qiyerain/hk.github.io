## Context

从面试角度整体审视 zfbbizriskagent（支付宝业务风险智能体平台）的架构设计，识别系统层面的不足并给出优化思路。该系统基于 Java 21 + SOFABoot + SOFA AI，作为 Agent 平台承载大量 LLM 调用、工具编排、DAG 执行等任务。

---

## 一、会话记忆 — 本地内存，无法水平扩展（严重）

**现状：** `WorkingMemoryServiceImpl` 用 `ConcurrentHashMap` 存储对话历史，纯本地内存。

**问题：**
- 多实例部署时会话不共享，用户请求被路由到不同机器会丢失上下文
- 无驱逐策略，长时间运行内存只增不减，有 OOM 风险
- Token 估算用 `length / 4`，不准确，可能导致上下文超限

**优化方向：**
- 会话存储迁移到 Redis/Tair，支持分布式部署
- 引入 TTL + LRU 淘汰策略
- 用 JTokkit（项目已有 `TokenCounterUtil`）替代硬编码估算

---

## 二、外部调用无熔断降级（严重）

**现状：** 70+ 工具直接调用外部服务（LLM API、ODPS、Lindorm、Maya、钉钉等），没有统一的熔断/降级机制。

**问题：**
- 某个外部服务故障时，调用线程阻塞堆积，引发级联失败
- 虚拟线程虽然不占 OS 线程，但连接池（100）会被耗尽
- LLM API 偶发超时/限流时，没有退避重试（仅 ChatModel 层有 retry，工具层没有）

**优化方向：**
- 在工具调用层引入 Resilience4j 熔断器（CircuitBreaker + Bulkhead）
- 工具基类 `AbstractAgentTool` 统一封装 try-catch + 熔断 + 超时
- LLM API 限流时自动降级（换模型/返回缓存结果/排队）

---

## 三、DAG 执行引擎缺少超时和资源保护（严重）

**现状：** `DefaultDagExecutor` 并行执行 DAG 节点，`ParallelExecutionStrategy` 用虚拟线程提交 CompletableFuture。

**问题：**
- DAG 整体执行无超时限制，某个节点卡住会导致整个 DAG 挂起
- `CompletableFuture.allOf().join()` 无超时版本被广泛使用
- Groovy 脚本条件评估无沙箱，存在任意代码执行风险

**优化方向：**
- DAG 级别设置总超时，节点级别设置单步超时
- 用 `waitForAllTasksWithTimeout()`（已有实现但未广泛使用）替代无超时版本
- Groovy 引擎加沙箱限制（禁用 System.exit、Runtime.exec 等）

---

## 四、限流与成本控制缺失（中等）

**现状：** 无显式限流机制，无 Token 成本追踪。

**问题：**
- 突发流量可能打穿 LLM API 配额
- 无法追踪每次请求/每个租户的 Token 消耗和成本
- 线程池 AbortPolicy 直接拒绝请求，无排队/降级

**优化方向：**
- 请求入口加令牌桶限流（全局 + 租户级）
- 基于 `TokenCounterUtil` 做请求级 Token 计量，落库统计
- 线程池拒绝策略改为 CallerRunsPolicy 或自定义排队策略

---

## 五、可观测性不足（中等）

**现状：** 只有 SLF4J 日志 + SOFA Tracer 基础链路追踪。

**问题：**
- 无 Metrics（QPS、P99 延迟、Token 消耗、工具调用成功率等）
- Agent 请求全链路（接收→LLM调用→工具执行→返回）缺少 Span 级追踪
- 无性能基线，SLA 无法量化

**优化方向：**
- 接入 Micrometer / OpenTelemetry，暴露关键指标
- Agent 执行链路埋点：每个 ReAct 轮次、每个工具调用、每次 LLM 请求
- 建立 Dashboard（LLM 延迟、工具成功率、Token 消耗趋势）

---

## 六、数据库层面问题（中等）

**现状：** OceanBase + MyBatis + ZDAL。

**问题：**
- 部分查询 `LIMIT 50000`（`PunishInfoDoMapper`、`PunishStatsMapper`），单次加载 5 万行
- extInfo 字段用 TEXT 存大 JSON（Agent 配置、DAG 定义、MCP 配置），OceanBase 不支持扩展到 LONGTEXT
- Service 层缺少 `@Transactional` 注解，事务边界不清晰

**优化方向：**
- 大批量查询改为游标分页（每次 500-1000）
- extInfo 拆分为独立配置表，或使用对象存储
- 关键业务操作（任务创建、状态流转）明确事务边界

---

## 七、SSE 流式输出的鲁棒性（低）

**现状：** `SseNotificationService` 实现了心跳（15s）和生命周期管理。

**问题：**
- 无背压机制，客户端消费慢时数据可能丢失
- 客户端异常断连时依赖心跳超时检测，有延迟
- `CopyOnWriteArrayList` 在大量连接时写操作（add/remove）开销大

**优化方向：**
- 引入消息缓冲队列，支持客户端重连后续传
- 断连检测从被动（等心跳失败）改为主动（TCP keepalive 探测）

---

## 八、安全问题（低但关键）

| 问题 | 位置 | 风险 |
|------|------|------|
| Groovy 脚本无沙箱 | `GroovyEdgeCondition` | 任意代码执行 |
| 工具参数无输入校验 | `ParamChecker` 仅注解校验 | 注入风险 |
| 工具输出无转义 | 存入 extInfo 后前端渲染 | XSS |

---

## 面试回答框架（总结）

> **一句话概括：** 系统功能完善（10+ Agent 类型、70+ 工具、DAG 编排、流式输出），但在**分布式能力、容错韧性、可观测性**三个维度有明显短板。
>
> **最想优先解决的三件事：**
> 1. **会话存储分布式化** — 这是水平扩展的前提
> 2. **外部调用熔断降级** — 这是生产稳定性的底线
> 3. **可观测性建设** — 这是发现和定位问题的基础
>
> **加分项可以提：**
> - DAG 超时保护、Groovy 沙箱（体现对安全和资源管理的敏感度）
> - Token 成本追踪（体现对业务成本的关注）
> - 大查询分页优化（体现对数据库性能的理解）
